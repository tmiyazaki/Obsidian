# 意思決定フレームワーク集

迷ったときの**判断軸**を集約。「**何を選ぶか**」より「**何を基準に選ぶか**」を共有する。

## 🎯 そもそもの判断

### この変更は必要か?

```
1. ユーザーが言った        → 採用判断には弱い (言うこと ≠ 使うこと)
2. データが示している       → 強い (ファネル離脱、ヒートマップ等)
3. 競合がやっている          → 中 (理由を確認)
4. ステークホルダーの希望   → 文脈次第
5. 技術的にできる            → 弱い (できる ≠ すべき)
```

→ [[../40-Bridge/Discovery-and-Validation]]

### 検証 vs 直接実装

| 検証する | 直接実装 |
|---|---|
| 大きな投資 | 小さな改善 |
| 慣れていない領域 | 慣習に従う |
| データに頼れない | 既知のベストプラクティス |
| 失敗の代償が大きい | 検証コスト > 実装コスト |

## 🏗 アーキテクチャ判断

### モノリス vs マイクロサービス

| モノリス | マイクロサービス |
|---|---|
| チーム < 10 人 | チーム > 30 人 |
| ドメイン未確定 | ドメイン安定 |
| 強整合性 | 部分的整合性で OK |
| デプロイ単位を統一 | チームごと独立 |
| 学習コスト低 | 高 |

**新規 SaaS は基本モノリスから始める**。マイクロサービス化は**チーム数で**スケールするまで待つ。

→ [[../10-Coding/Architecture-Layers]]

### REST vs GraphQL vs gRPC vs tRPC

| | 強み | 用途 |
|---|---|---|
| **REST** | HTTP インフラ、CDN | パブリック API |
| **GraphQL** | フィールド指定、強い型 | 多端末 + 多形状 |
| **gRPC** | 高性能、ストリーム | 内部マイクロサービス |
| **tRPC** | TypeScript 型貫通 | 内部 (TS のみ) |

→ [[../10-Coding/API-Design]]

### DB 選択

| 用途 | 推奨 |
|---|---|
| 標準 OLTP | PostgreSQL (第一選択) |
| 大規模分析 | BigQuery / Snowflake / ClickHouse |
| キャッシュ・セッション | Redis |
| 全文検索 | Elasticsearch / Meilisearch |
| ベクトル | pgvector / Pinecone |
| グラフ | Neo4j (ニッチ) |
| ドキュメント | MongoDB (慎重に) |

新規は**Postgres から**。スケールで**追加**(置換でなく)。

→ [[../10-Coding/Database-Design]]

### キャッシュ層の選択

| データ | 層 |
|---|---|
| 静的アセット | CDN (1 年 + cache busting) |
| SSR HTML | CDN (短時間 + SWR) |
| API レスポンス | CDN or Redis (個人化なら 後者) |
| 計算結果 | Redis or アプリ内 LRU |
| DB クエリ結果 | アプリ内 LRU or Redis |

→ [[../10-Coding/Caching-Strategies]]

### Edge vs Origin

| Edge | Origin |
|---|---|
| 認証チェック | 重い計算 |
| A/B 振り分け | DB 大量アクセス |
| 簡単な変換 | ML 推論 |
| 静的配信 | ステートフル |

レイテンシ要件 + 計算量で判断。

→ [[../10-Coding/Edge-and-Distributed]]

## 💻 コード判断

### State の置き場

| 性質 | 置き場 |
|---|---|
| サーバーから取得 | TanStack Query / SWR |
| UI ローカル | useState |
| 中規模、頻繁更新少 | Context |
| 大規模 | Zustand / Redux Toolkit |
| 複雑遷移 | XState |
| URL に出すべき | クエリパラメタ |

→ [[../10-Coding/State-Management]]

### 例外 vs Result 型

```
業務ルール違反 (在庫不足)         → Result 型
プログラムバグ (NPE)              → 例外で fail fast
一過性障害 (ネットワーク)         → リトライ + サーキットブレーカ
入力エラー                        → 早期に拒否
```

→ [[../10-Coding/Error-Handling]]

### OOP vs FP

```
ビジネスルール、ドメイン       → 関数型寄り (純粋・不変)
UI コンポーネント              → 関数型 (React)
ステートフルなサービス          → OOP (クラス)
```

「**Functional Core, Imperative Shell**」が現実解。

→ [[../10-Coding/Functional-Programming]]

### Soft Delete vs Hard Delete

| Soft Delete | Hard Delete |
|---|---|
| 復元・監査が必要 | 復元不要 |
| 履歴・分析を残す | GDPR 削除権 |
| 全クエリに条件追加 | クリーンな DB |

両者の中間: **アーカイブテーブル**(本テーブルからは消し別所に保持)。

→ [[../10-Coding/Database-Design]]

## 🎨 デザイン判断

### 整列 vs 破調

| 整列 | 破調 |
|---|---|
| 業務系 | LP / メディア |
| ダッシュボード | ヒーロー |
| 一覧・テーブル | 一点モノ |
| 機能優先 | 印象優先 |

1 サービス内で**混在 OK**(役割ごと)。

→ [[../20-Design/Editorial-Expressive-Layouts]]

### 描画レイヤ選択

```
1. CSS で済むか?              → 済むなら CSS
2. SVG で済むか?              → ベクトルなら SVG
3. 大量要素・自由形か?        → Canvas 2D
4. 3D / カスタムシェーダか?   → WebGL
```

下層ほどコスト高。**上から検討**。

→ [[../20-Design/Creative-Coding-Canvas-WebGL]]

### イラスト vs 写真

| 写真 | イラスト |
|---|---|
| 顧客事例、人物 | 概念、機能説明 |
| 信頼感 | ブランド色追従 |
| 撮影コスト | 制作コスト |

両方使うなら**役割を分ける**。

→ [[../20-Design/Illustration-Photography]]

### ライト vs ダーク (デフォルト)

```
1. System (auto)  ← 推奨デフォルト
2. Light (強制)
3. Dark (強制)
```

両モード提供 + System 連動。

→ [[../20-Design/Dark-Mode]]

## 🖱 インターフェース判断

### モーダル vs プッシュ vs シート vs ページ

| 用途 | UI |
|---|---|
| 同フロー内、戻れる | プッシュ (画面遷移) |
| 別タスク、閉じる | モーダル |
| 一時操作、スマホ | ボトムシート |
| 情報量大、深い | 別ページ |
| 短い通知 | Toast |

→ [[../30-Interface/Interaction-Patterns]]

### 即時保存 vs 明示保存

| 即時 (Auto-save) | 明示 (Save button) |
|---|---|
| トグル、選択 | 複雑フォーム |
| 単純設定 | 多項目編集 |
| 取り消し可 | プレビュー |

混在禁止 (1 サービス内で統一)。

→ [[../30-Interface/Settings-Preferences]]

### ページネーション vs 無限スクロール vs 仮想

| | 用途 |
|---|---|
| ページネーション | 業務系・テーブル・SEO |
| 無限スクロール | フィード・閲覧 |
| 仮想スクロール | 1 万行超のデータ |

→ [[../30-Interface/Tables-Data-Grids]]

### コンバセーショナル vs 通常 UI

```
構造化データの一覧            → テーブル
複雑な空間操作                → 直接操作
正確な日付・色選択            → 専用ピッカー
複雑な要求の表明              → 自然言語 (会話)
学習コストの低い操作          → ボタン UI
```

「会話で何でも置換」は失敗。**ハイブリッド**が正解。

→ [[../30-Interface/Conversational-UI]]

## 👥 チーム判断

### 機能を作る? 削る? 直す?

```
バグ修正                      → ほぼ常に直す (信頼)
古い機能 (使われていない)    → 削る (複雑度低減)
新機能要望                    → 検証 (4 リスク評価)
パフォーマンス問題             → 計測してから判断
```

→ [[../40-Bridge/Tech-Debt]] / [[../40-Bridge/Discovery-and-Validation]]

### 自作 vs ライブラリ vs SaaS

| 自作 | ライブラリ | SaaS |
|---|---|---|
| コア競争力 | 周辺機能 | 周辺サービス |
| 完全制御 | カスタマイズ可 | 即時運用 |
| 工数大 | 中 | 小 |
| 長期安心 | 依存リスク | ロックイン |

**90% は SaaS / OSS で済むはず**。コア(差別化要素)だけ自作。

→ [[../40-Bridge/Tool-Stacks-Recipes]]

### ロードマップに乗せる? 乗せない?

```
Now (確定)            : 確度高、即着手
Next (準備中)         : 検証 / 設計中
Later (検討中)        : アイデア
Won't Have (今期外)   : 期待管理
```

→ [[../40-Bridge/Roadmapping-Prioritization]]

### 技術的負債を返す? 返さない?

| 返す | 返さない |
|---|---|
| 触る頻度高 | 二度と触らない |
| 利息が事業速度を阻害 | 近々書き換え予定 |
| ロックインで新機能不可 | ROI 低い |
| セキュリティリスク | |

→ [[../40-Bridge/Tech-Debt]]

## 🌍 倫理・社会判断

### このデータ集めるべき?

```
本当に必要か?
   ↓
最小精度・期間で済むか?
   ↓
ユーザーの利益と整合か?
   ↓
削除権・透明性を提供できるか?
   ↓
規制 (GDPR/個人情報保護法) を満たすか?
   ↓
それでも必要なら集める
```

→ [[../40-Bridge/Privacy-by-Design]]

### この施策はダークパターンか?

```
拒否が承認と同等の手数か?
   ↓
ユーザーの長期幸福と整合か?
   ↓
透明・撤回可能か?
   ↓
情報を歪めていないか?
   ↓
全部 Yes なら倫理的、No があれば見直し
```

→ [[../40-Bridge/Ethical-Design]]

### A/B テストの結果は採用すべき?

```
✓ 短期 KPI 改善
✓ 長期定着 (リテンション) も維持
✓ 副次悪化なし (CS 問い合わせ等)
✓ 統計的有意 + 検出力十分
✓ 倫理・アクセシビリティに反していない
```

5 つすべて Yes でないと採用しない。

→ [[../40-Bridge/Discovery-and-Validation]]

## 🤖 AI / LLM 判断

### LLM を使うべきか

| 使う | 使わない |
|---|---|
| 自然言語の理解・生成 | 確定的計算 |
| 多様な入力 | 単純なルール |
| クリエイティブ | 厳密性必須 (会計、法的) |
| 補助的役割 | 主機能(リスク高) |

「**LLM = 確率的・遅い・誤る**」を前提に**人間の確認を組み込む**。

→ [[../30-Interface/AI-LLM-Interfaces]]

### モデルサイズの選択

```
速度・コスト重視  → Haiku 4.5
バランス          → Sonnet 4.6
深い思考          → Opus 4.7
ローカル実行      → Llama 3 / Phi 等
```

タスク複雑度で使い分け。**全部 Opus** はコスト過剰。
