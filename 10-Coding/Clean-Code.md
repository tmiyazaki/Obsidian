# クリーンコード原則

## 一行で

> コードを「動く」状態から「**意図が読める**」状態へ引き上げるための、日常的な書き方の作法。

## なぜ重要か

ソフトウェアのコストの大半は**書く時間ではなく読む時間**に費やされます。Robert C. Martin はこれを「読み書き比 10:1」と表現しました。1 行を書くために 10 行を読む。だからこそ、書き手は読み手のために最適化すべきです。

「動く汚いコード」と「動く綺麗なコード」のあいだには、変更コストに 10〜100 倍の差が生まれます。

## 中核となる原理

### 1. 命名は最大のドキュメント

- **意図を表す名前** — `d` ではなく `daysSinceLastLogin`
- **誤誘導しない名前** — `accountList` が `Set` なら嘘
- **発音できる名前** — チームで会話に乗る名前
- **検索できる名前** — `MAX_CLASSES_PER_STUDENT` は grep できるが `7` は埋もれる

詳細: [[Naming]]

### 2. 関数は小さく、ひとつのことを

- 1 関数 ≒ 1 段の抽象化レベル
- 引数は 0〜2 個が理想、3 個で警戒、4 個以上は分解候補
- フラグ引数 (`doSomething(true)`) は 2 つの関数の合成 — 分けろ
- 副作用を関数名に含めるか、純粋関数として括り出す

### 3. コメントは敗北宣言になりうる

良いコメントの条件:
- **なぜ**を語る (コードは**なに/どう**を語る)
- 法的・契約的な明示
- 後々のための警告 (`// TODO`, `// HACK` には期限を)

悪いコメント:
```js
// ユーザーIDを取得する
const userId = getUserId();   // ← 関数名で読める。冗長。
```

### 4. ボーイスカウト・ルール

> 「キャンプ場は来たときよりも綺麗にして帰る」

PR で触れたファイルは、出ていくとき少し綺麗になっているべき。**大規模リファクタはコミットを分ける**。混ぜると読み手が混乱する。

### 5. DRY と WET のバランス

- DRY (Don't Repeat Yourself): 知識の重複を避ける
- 早すぎる抽象化は WET より有害 — **3 度同じパターンが現れてから抽象化**(Rule of Three)
- 「形が似ている」と「同じ知識である」は別物

## 実践

### 良い例

```ts
function isEligibleForDiscount(customer: Customer): boolean {
  return customer.isReturning && customer.totalSpend > LOYALTY_THRESHOLD;
}
```

- 真偽値を返す関数は `is/has/can` で始める
- 定数で意図を露出
- Boolean 式に名前を与える(将来 if 文に直接書かない)

### 反面教師

```ts
function check(c: any): boolean {
  // 既存ユーザーかつしきい値超え
  if (c.r === true) {
    if (c.t > 100) return true;
  }
  return false;
}
```

問題: 名前が無意味、`any`、ネストが深い、マジックナンバー、コメントで意図を補強(命名で済ませろ)。

## よくある誤解

- ❌ コメントを増やすほど親切
- ✅ コメントは**コードでは表現できない情報**にだけ使う

- ❌ 短い関数に分割するほど偉い
- ✅ 抽象化レベルが揃うように分ける。むやみに分けるとジャンプが増えて逆に読みにくい

- ❌ Clean Code は「正解の集合」
- ✅ **トレードオフの語彙集**。状況により答えは変わる

## チェックリスト

- [ ] 関数名から「何が起きるか」推測できる
- [ ] 1 関数のスクロールが不要(画面に収まる)
- [ ] マジックナンバー/マジックストリングに名前がついている
- [ ] 「なぜ」のコメントは残し、「なに」のコメントは削った
- [ ] 公開 API の引数順序は呼ぶ側にとって自然か
