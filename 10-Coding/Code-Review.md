# コードレビュー

## 一行で

> レビューは「**バグ探し**」ではなく「**コードベースを集合知で育てる対話**」。

## なぜ重要か

レビューには 4 つの効果がある:

1. **欠陥検出**: バグ・脆弱性を本番前に潰す
2. **知識の共有**: コードベースの理解者を増やし、属人性を下げる
3. **基準の共有**: 暗黙のスタイル・設計原則を可視化する
4. **教育**: シニアからジュニアへ、ジュニアからシニアへ(視点が違うので双方向)

レビューを「ゲートキーピング」と捉えると殺伐とし、**共著作業**と捉えると育つ。

## レビュアーの心得

### 1. コードを攻撃せず、設計を議論する

```
❌ "This code is bad."
✅ "I find this hard to follow because X. Could we try Y?"
```

主語を「私」にする。`I` ステートメントは指摘を意見として伝え、相手の防衛反応を下げる。

### 2. 質問の形で介入する

```
❌ "You should split this function."
✅ "What do you think about extracting the validation block?
     I worry the function does two things now."
```

レビュアーは作者ほど文脈を持たない。**断定を避け、提案にする**。

### 3. 重要度を明示する

```
[blocking] このパスは認証が抜けています
[suggestion] 命名を `userIds` にすると単複が明確
[nit] 末尾の空白が一つ多いです(自動整形でOK)
[question] この設計を選んだ背景を知りたい
```

ラベル付けにより、作者は「直さねば」と「気が向いたら」を区別できる。

### 4. 良いところを言う

「ここの抽象化がきれい」「テストの観点が抜けてなかった」など**positive な言及**は、批判の信頼を支える。レビューが「指摘の場」だけになると、作者は最小サイズの PR しか出さなくなる(=学習機会の損失)。

## 作者の心得

### 1. PR を小さく保つ

レビュー品質は PR サイズに**反比例**する(研究的にも 200 行を超えると検出率が落ちる)。大きな仕事は**段階的 PR**に分ける:

- リファクタリング先行(振る舞いを変えない)
- 機能追加(小さな単位で)
- ドキュメント

### 2. 自分でセルフレビューしてから出す

PR を開いた瞬間に**自分で diff を眺める**。8 割の指摘事項は自分で見つけられる。

### 3. 文脈を PR 説明に書く

- **なぜ**この変更が必要か
- **何を**変えたか
- **どう**確認したか(動かし方、影響範囲)
- 既知の **未解決事項**

レビュアーがコードに辿り着く前に文脈が伝わるべき。

### 4. 反応は「受け止める」「議論する」「却下する」を分ける

すべてを受け入れる必要はない。但し却下するときは**理由を返す**。沈黙はレビュアーへの最悪のフィードバック。

## レビューで見る 5 階層

| 層 | 観点 |
|---|---|
| 1. 設計 | この変更はそもそも正しい場所にあるか |
| 2. 機能 | 仕様を満たすか、エッジケースは |
| 3. 複雑性 | 不必要に複雑でないか、もっと単純にできないか |
| 4. 命名/可読性 | 半年後に読んで分かるか |
| 5. テスト | 変更を守るテストが付いているか |

スタイルは自動整形に任せる。**人間は人間にしかできない議論**に集中する。

## 自動化に任せる(人間レビューの先)

- フォーマッタ (Prettier, gofmt, ruff format)
- リンタ (ESLint, Pylint, golangci-lint)
- 型チェッカ
- セキュリティスキャン
- カバレッジ閾値

これらが緑であることを**マージの前提条件**にすると、レビューの質が上がる。

## アンチパターン

- **rubber stamp**: 内容を読まずに LGTM
- **bike shedding**: 些末な命名議論で本質的な設計議論を避ける
- **chasing the carrot**: 修正→再リクエスト→新しい指摘→修正… の無限ループ(新指摘は別 PR で出す合意を)
- **大量 PR**: 1000 行超えはレビューが形骸化

## チェックリスト(レビュアー)

- [ ] 設計上の懸念はあるか
- [ ] 仕様は満たすか、テストは妥当か
- [ ] 命名・構造で読みづらい部分は指摘したか
- [ ] 重要度ラベルをつけたか
- [ ] 良かった点を 1 つ以上言ったか

## チェックリスト(作者)

- [ ] PR サイズは妥当か(目安 < 400 行)
- [ ] PR 説明に「なぜ」「何を」「どう確認」を書いたか
- [ ] セルフレビュー済みか
- [ ] CI 緑か
