# デザインシステム

## 一行で

> デザインシステムは「**プロダクトを作り続けるための共通言語と部品**」。ライブラリではなく**継続する社会的契約**である。

## なぜ重要か

人数とプロダクト数が増えると、UI は**同じ問題を再発明し続ける**スパイラルに入ります。デザインシステムは、再発明を**部品化・規約化**することで、開発速度・品質・ブランド一貫性を底上げします。

ただし、システムを**作ること**自体が目的化すると失敗します。**消費される回数**で価値が決まります。

## 構成要素

### 1. 原則 (Principles)

「我々は何を信じるか」 — 判断のとき立ち戻る道標。
- 例: 「明瞭さは美しさに優先する」「アクセシビリティは機能の一部」

### 2. デザイントークン

→ [[Design-Tokens]]

### 3. ファウンデーション

色、タイポグラフィ、余白、グリッド、エレベーション、モーション、ボイス&トーン。

### 4. コンポーネント

ボタン、フォーム、ナビゲーション、ダイアログ、テーブル等。
- **API**: props (variant, size, state)
- **挙動仕様**: hover, focus, disabled, loading
- **アクセシビリティ**: ARIA、キーボード、フォーカス可視

### 5. パターン

複数コンポーネントで構成される定型解。
- 検索結果ページ、空状態、確認モーダル、エラーフロー

### 6. ガイドライン

「いつどれを使うか」を書く。**コンポーネントが何を解決するかではなく、どの場面で選ぶかが本体**。

### 7. ガバナンス

- 提案 → レビュー → 承認 → 実装 → リリース
- 「コアチーム + コントリビューションモデル」が現実的
- バージョニングと breaking change の扱い

## Atomic Design(構造の語彙)

Brad Frost のフレーム:

```
原子 (Atoms)         ボタン、入力、ラベル
分子 (Molecules)      ラベル + 入力 + ヘルプテキスト
有機体 (Organisms)    ヘッダー、フォーム
テンプレート          ページの骨格
ページ                データを当てた具体例
```

**正しいかどうか**より「**チームで共有できる粒度の言葉**」を持つことが価値。
過度に教条主義になる必要はない。

## 採用と運用

### 育てる順序

1. **観察** — 既存プロダクトから繰り返し現れるパターンを洗い出す
2. **抽出** — 共通化できる粒度を見極める
3. **標準化** — トークン・コンポーネントとして公開
4. **採用** — 使ってもらう(難所はここ)
5. **改善** — 利用フィードバックで進化

### 「採用されない」を防ぐ

- ドキュメントは**コードと同じリポジトリ**に置く(乖離防止)
- **使うほうが楽**でないと採用されない(摩擦を最小に)
- 例外時の**逃げ道**を用意(custom prop, slot, escape hatch)
- リリースノートを**毎回書く**

### Storybook / 同等ツール

コンポーネントを**実装として動かしながら文書化**する。Visual Regression テストの基盤にもなる。

### コントリビューションフロー

```
issue 起票 → 議論 → デザイン → 実装 → レビュー → リリース
```

中央集権的に閉じすぎると採用が広がらない。**コアチームはレビュアー**として動き、貢献者を増やす。

## バージョニング

Semantic Versioning に従う:
- **major**: 既存利用が壊れる(prop 削除など)
- **minor**: 機能追加
- **patch**: バグ修正

破壊的変更時は**移行ガイド**(codemod があると尊敬される)。

## アンチパターン

- **ライブラリだけ**で原則・ガイドライン無し → 部品の選び方が分からず破綻
- **デザインと実装が別管理** → トークンや仕様が乖離
- **コアチームが密室で決める** → 現場の声が届かない
- **すべて完璧にしてから公開** → リリースされない
- **過度に汎用化** → API が複雑化、誰も使えない
- **古い API を消さない** → 新旧が両立して混乱

## 成功指標

- コンポーネントの**採用率** (重複コンポーネントの存続率)
- リリースノートの**頻度**
- ステークホルダの**理解度**(用語が会話で使われる)
- 新メンバーが**何日で機能を出せるか**

## チェックリスト

- [ ] 原則・トークン・コンポーネント・パターンが**揃って**いるか
- [ ] ドキュメントが**最新**か(コードとの乖離がないか)
- [ ] アクセシビリティ要件が**コンポーネントに組み込まれて**いるか
- [ ] バージョニング/移行ガイドの仕組みがあるか
- [ ] コントリビューションが**現実的に可能**な仕組みになっているか
