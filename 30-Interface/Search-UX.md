# 検索 UX

## 一行で

> 検索は「**ナビが届かない場所への近道**」。良い検索は IA の補完、悪い検索は**逃げ場**。

## なぜ重要か

ユーザーがナビで迷ったら検索に逃げます。検索が機能すれば救われ、機能しなければ離脱します。コンテンツ量が増えるほど検索の重要性は上がり、コンテンツプロダクト/EC/SaaS では**主要な発見手段**になります。

## 良い検索の階層

```
1. キーワードが当たる             ← 最低限
2. 同義語・誤字を許す
3. 関連順にランキング
4. 候補を予測 (suggest)
5. ファセットで絞り込める
6. 結果ゼロでも前進できる
7. 履歴 + 文脈 + パーソナライズ
8. 自然言語クエリ理解 (LLM)
```

下から積み上げる ─ 1 ができていないのに 7 を作っても意味がない。

## クエリ入力 UX

### 検索ボックスの位置

- **常設** (ヘッダ右上 / 中央): SaaS、コンテンツ
- **アイコン → 展開** (モバイル / シンプル UI)
- **専用ページ** (Google 型 / 検索が中心の場合)

検索が頻繁に使われるなら**常設**。クリック 1 回減らすだけでアクセス数は跳ねる。

### Cmd/Ctrl+K (コマンドパレット)

開発者ツールから広がった慣習。SaaS では事実上の標準:

```
[ Cmd+K ]
  ↓
[ 検索 + ナビ + アクション全部 ]
```

`Algolia DocSearch`, `cmdk` ライブラリで簡単に実装可能。

### プレースホルダ

例を見せる:

```
✗ "検索"
✓ "プロジェクト名、タグ、ユーザーで検索..."
```

何を検索できるか**予測**できる。

### サジェスト (Type-ahead)

入力中に**候補を表示**:

- 直近検索
- 人気検索
- 入力先頭一致 (オートコンプリート)
- 結果プレビュー (最初の数件)

```
Q: "デザ"
   ↓ サジェスト
   - デザイン
   - デザインシステム
   - デザインパターン (前回検索)
   ─────────
   結果プレビュー:
   - Visual-Hierarchy
   - Design-Tokens
```

### キーボードナビゲーション

- ↑↓ で候補移動
- Enter で選択
- Esc で閉じる
- Tab で次のフィールドへ

## ランキング

「**関連順**」は単純ではない。複数の信号を重み付け:

- **キーワード一致** (タイトル > 本文 > タグ)
- **完全一致 vs 部分一致**
- **新しさ** (最近のものを優先)
- **人気度** (クリック・閲覧)
- **個人化** (過去の利用)
- **権限** (見れないものは出さない)

検索エンジン (Elasticsearch, Meilisearch, Algolia, Typesense) はこれらを**スコアリング**で組み合わせる。

## ファセット (絞り込み)

複数条件で結果を狭める:

```
[ Q: "Blue" ]   結果 142 件

カテゴリ
  ☐ シャツ (45)
  ☐ パンツ (12)
  ☐ アクセサリー (88)

価格帯
  ☐ ¥0-1000
  ☐ ¥1000-3000
  ☐ ¥3000+

色
  ☐ ライトブルー (42)
  ☐ ネイビー (60)
  ☐ ターコイズ (15)
```

EC、求人、不動産、論文検索の標準。

### ファセット設計の原則

- **件数を表示**(0 件のフィルタは選ばせない)
- 適用済みフィルタを**チップ表示**(削除可)
- 「**すべて解除**」リンク
- モバイルではボトムシートで分離

## 結果表示

### スニペット (前後文脈)

検索キーワードを**ハイライト**して、前後 1〜2 行を抜粋:

```
タイトル: Visual Hierarchy
…**視覚階層**は読み手の目線を…
[更新: 2026-04-02]
```

「**なぜこれがヒットしたか**」が一目で分かる。

### グルーピング

カテゴリ別に分けて表示:

```
ノート (12)
  - Visual-Hierarchy
  - Typography
  ...

タグ (3)
  - #design

ユーザー (2)
```

### 件数の明示

```
[ 検索結果: 「デザイン」  142 件中 1-20 件目 ]
```

総数があると安心 (本当に**全部**を見ている?)。

## ゼロ結果 (No Results)

検索の**最も重要な失敗パス**。「見つかりませんでした」だけは不親切。

```
"プロジエクト管理" の結果がありません

もしかして:
  • プロジェクト管理 (誤字訂正) ← クリックで再検索

検索範囲を広げる:
  • [ 過去のアーカイブを含める ]
  • [ フィルタをリセット ]

それでも見つからない場合:
  • [ 新規作成 ]  [ サポートに問い合わせる ]
```

「**次にできること**」を必ず提示。

## 履歴と保存

- **直近検索** (最近の 5 件、バッジ + 削除可)
- **保存検索** (頻繁な複合クエリ)
- **アラート** (新しい結果が出たら通知)

ECや求人ではユーザーを**戻ってこさせる**仕掛けに。

## 高度なクエリ

Power user 向けに**演算子**を提供:

```
status:open assignee:me priority:high
"完全一致フレーズ"
-除外したい単語
```

Notion / GitHub / Gmail のスタイル。**ヘルプから学べる**ようにし、サジェストで自動補完すると敷居が下がる。

## 自然言語 / LLM 検索

→ [[AI-LLM-Interfaces]]

「先月の支払い済み注文の合計は?」を SQL や API クエリに変換する LLM レイヤ。
- ただし**結果の根拠**を必ず示す
- 古典的検索を**併用**(LLM が外したときの保険)

## アクセシビリティ

- 検索ボックスに `<label>` (見えなくても `aria-label`)
- `role="search"` で landmark 化
- サジェストリストに `role="listbox"`, 候補に `role="option"`
- `aria-live` で「N 件見つかりました」をアナウンス

→ [[Accessibility]]

## パフォーマンス

- 入力中検索は **debounce 200〜300ms**
- 軽い結果は**キャッシュ**
- 大規模はサーバ側 + 検索エンジン
- インデックス更新は**書き込みと非同期**

→ [[../10-Coding/Performance]]

## 計測と改善

何を測るか:
- 検索 → クリック率
- ゼロ結果率 (高いと UX 悪、または辞書不足)
- 検索後のセッション継続率
- 検索クエリの**ログ** (頻出語、失敗語の発見)

「**よく検索されるが結果が出ない**」語彙はコンテンツ追加 or 同義語辞書に追加すべき信号。

## アンチパターン

- プレースホルダ「検索」だけ
- 完全一致のみで**誤字を許さない**
- ゼロ結果で「ありません」だけ
- フィルタの件数を出さず**0 件のフィルタ**を選ばせる
- スマホで**全機能再現**して破綻
- 検索結果に**権限のないもの**まで出る (情報漏洩)
- 重い同期処理で入力遅延

## チェックリスト

- [ ] 検索が**主要画面**から到達可能か (Cmd+K 含む)
- [ ] サジェスト + 直近検索があるか
- [ ] 結果に**スニペット + ハイライト**があるか
- [ ] ゼロ結果で**次の行動**を示しているか
- [ ] ファセットに**件数**が表示されているか
- [ ] 誤字・同義語を**ある程度**許すか
- [ ] 検索クエリのログから**改善サイクル**が回っているか
