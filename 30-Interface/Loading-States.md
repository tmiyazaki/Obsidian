# ローディング状態

## 一行で

> 待ち時間は**避けられない**が、**感じ方は設計できる**。「何も起きてない」と「進んでいる」の差が UX を分ける。

## なぜ重要か

人間は不確実性を嫌います。「押したけど反応がない」状態は、**実際の遅延以上に長く感じられる**。逆に、進捗が見える待ちは耐えられる。Loading State は**透明性**と**予測可能性**の設計です。

## 待ち時間の体感則

| 時間 | 推奨 |
|---|---|
| 0–100ms | 即時。何もしない |
| 100–300ms | スピナーは**チラつく**。何もしないか、ボタンの押下感だけ |
| 300ms–1s | スピナー / 微小アニメ |
| 1–10s | 進捗バー or スケルトン |
| 10s+ | 進捗 + 残り時間 + キャンセル |

「**1 秒以上の待ち**には**進捗の知覚**が必要」を覚える。

## バリエーション

### 1. スピナー (Spinner)

汎用的、軽い。ただし**サイズと数を抑制**。1 ページに 5 つ回っているとカオス。

### 2. スケルトン (Skeleton Screen)

実際のレイアウトを灰色のプレースホルダで描画。
- **何が来るか**を予測できる(レイアウトが固定)
- 体感速度を上げる(コンテンツが「ある」と認知)
- レイアウトシフトを避けやすい

```css
.skeleton {
  background: linear-gradient(90deg, #eee, #ddd, #eee);
  background-size: 200% 100%;
  animation: shimmer 1.5s infinite;
}
@keyframes shimmer { from { background-position: 200% 0; } to { background-position: -200% 0; } }
```

### 3. 進捗バー (Progress Bar)

- 確定的進捗(ファイルアップロード等): 実進捗を表示
- 不確定進捗: パーセントを偽装しない。**不定**であることを示す

### 4. プレースホルダ・コンテンツ

「読み込み中…」というテキストではなく、**前回のキャッシュ**を即時表示し、新しいデータが来たら差し替える(Stale-While-Revalidate)。

### 5. Optimistic UI

サーバー応答を待たず、成功した前提で UI を更新。失敗時にロールバック。
- いいね・お気に入り
- リスト追加
- 短文投稿

→ [[Interaction-Patterns#Optimistic-UI|Optimistic UI]]

## 全体構造としての 5 状態

UI コンポーネントは**最低 5 状態**を設計する:

```
1. Empty   — データが無い (新規ユーザー)
2. Loading — データ取得中
3. Partial — 一部読み込めた
4. Error   — 失敗した
5. Ideal   — 完全に表示できた
```

エンジニアは Ideal を作って終わりがち。デザイナーは Empty/Error を含めて**5 つ全て**のスケッチを要求する。

## エラー状態の設計

→ [[../10-Coding/Error-Handling]]

UI 観点では:

- **何が起きたか**を平易な言葉で
- **次に何ができるか**(再試行ボタン、別ルート)
- **誰の責任か**(ユーザーの入力ミスなのか、システム障害なのか)
- 技術的詳細は**展開可能**な形で隠す(開発支援用)

```
[ ⚠ ] 通信に失敗しました

  ネットワーク接続を確認のうえ、もう一度お試しください。
  問題が続く場合は support@example.com までご連絡ください。

  [ 再試行 ]   [ 詳細を表示 ▼ ]
```

## 空状態 (Empty State)

「**データがない画面**」は**最も誤解されやすい**:
- バグなのか、本当に空なのか分からない
- 新規ユーザーは何をすべきか分からない

設計要素:
- **理由**: 「まだ投稿がありません」「フィルタに合う結果がありません」
- **次の行動**: 「最初の投稿を作成」「フィルタをリセット」
- **トーン**: 軽い図やイラストで威圧感を緩和

## レイアウトシフト (CLS) を防ぐ

- 画像・iframe・動画には `width / height` 属性
- 動的に挿入されるバナーは**領域を予約**
- フォントの **FOUT/FOIT** を抑える(`font-display: swap` + サブセット化)

CLS が 0.1 を超えると Core Web Vitals が悪化し、Google ランキングにも影響。

## 並行処理と段階表示

複数の API を同時に呼ぶ場合:

```
ヘッダー (即時) → 本体 (300ms 後にスケルトン → 本物) → 関連記事 (1s 後)
```

**重要な領域から順次**埋まる方が、全部一斉に出るより速く感じる。

## アンチパターン

- 100ms 未満のチラつくスピナー
- 「Loading…」テキストだけが何秒も
- 進捗 % を偽装して急に 99% で停止
- エラーで**何も表示されない**(ホワイトアウト)
- Empty State が「No data」だけ
- レイアウトシフトでクリック先がズレる

## チェックリスト

- [ ] 各画面に **5 状態**(空/読込/部分/エラー/理想)が設計されているか
- [ ] 1 秒以上の待機に**進捗の知覚**があるか
- [ ] 100ms 未満のチラつきを避けているか
- [ ] エラーが「何が起きて、次に何をするか」を伝えるか
- [ ] レイアウトシフトを起こさないか
- [ ] Optimistic UI のロールバック設計があるか
