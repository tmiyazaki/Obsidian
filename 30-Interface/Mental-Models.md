# メンタルモデルと認知負荷

## 一行で

> ユーザーは UI をシステム仕様で操作するのではなく、**自分の頭の中のモデル**で操作する。良い設計はそのモデルに**沿う**か、丁寧に**作り変える**。

## なぜ重要か

機能が同じでも、ユーザーの**期待**と**振る舞い**がずれているとき UI は失敗します。「ここをクリックするとこうなるはず」「戻るボタンで前の状態に戻るはず」── この期待を裏切ると、たとえ機能が動いていても**壊れている**と感じられる。

## 3 つのモデル (Norman)

```
[ デザインモデル ]      ← 設計者が意図したシステム
       ↓
       ↓ システムイメージ (UI、ドキュメント、文言)
       ↓
[ ユーザーモデル  ]      ← ユーザーの理解
```

設計者が直接ユーザーモデルに介入することはできず、**システムイメージ (= UI そのもの)** を通してしか伝えられない。これが UI の仕事の本質。

## メンタルモデルの源泉

ユーザーの期待は無からは生まれない:

- **過去の経験** (他アプリ、物理的な道具)
- **比喩・メタファ** (デスクトップ、ファイル、フォルダ)
- **学習** (使ううちに身につく)
- **文化的慣習** (左 = 戻る、上 = 重要)

設計は**過去の経験を活用**するか、**新しい経験を構築**するかの選択。後者はコストが高い。

## アフォーダンスとシグニファイア

→ [[UX-Principles#アフォーダンスとシグニファイア]]

- **アフォーダンス**: 物理的にできること (ボタンは押せる)
- **シグニファイア**: 「できる」ことを示す手がかり (押せそうに見える形)

フラットデザインの罠: シグニファイアが消え、何が押せるか分からない。**ボタン = 高さ・縁・押せそうな質感**を保つ。

## 概念モデルの設計

### 1. メタファを選ぶ

ファイル/フォルダ、トラッシュ、デスクトップ ── これらはコンピュータの物理メタファ。
新しい機能を作るとき、**何のメタファを採用するか**を決める。

```
SaaS の「Workspace」 = 部屋
  └ メンバー = 同居人
  └ プロジェクト = 棚
  └ タスク = 紙
```

メタファが選べたら、文言・アイコン・操作がメタファに沿うか確認。

### 2. メタファの限界を認める

メタファに**過剰に縛られない**。「フォルダ」を厳密に守ると、**1 つのものが複数の場所にある** (タグ的) を実装できない。
メタファは出発点、限界は別の手段 (タグ・リンク・ショートカット) で補完。

### 3. 一貫性

同じものは**同じ振る舞い**で。「ドラッグで移動」が一部だけだと、ユーザーは**全部できる**と期待して落胆する。

## 認知負荷の 3 種

| 種類 | 内容 | 設計で何をすべきか |
|---|---|---|
| **Intrinsic** | 課題本来の難しさ | 構造化・段階化で軽減 |
| **Extraneous** | 余計な負荷 (雑な UI 等) | **削減** が最重要 |
| **Germane** | 学びに繋がる負荷 | 適度に残す |

Extraneous の削減が UX 改善の主戦場。

## ヒックの法則 (Hick's Law)

> 選択肢が増えるほど、決定に時間がかかる。

```
T = a + b·log₂(n)
```

メニュー項目を増やすと、**全項目が遅くなる**。対策:
- カテゴリでグルーピング
- 段階的開示 (詳細を畳む)
- スマートデフォルト (90% が選ぶものを初期値)

## フィッツの法則 (Fitts's Law)

> ターゲットへの到達時間は、距離に比例し、サイズに反比例する。

```
T = a + b·log₂(D/W + 1)
```

実用への帰結:
- **大きいボタン** = 速く押せる
- **画面端**は無限大の幅 (マウスが止まる) → スマホのボトムナビ、デスクトップのメニューバー
- 主要 CTA は**大きく・近く**
- 危険な操作 (削除) は**遠く・小さく**配置 (誤操作を防ぐ)

## ミラーの法則と短期記憶

> 短期記憶は **7 ± 2** チャンク。

近年は **4 ± 1** とされることも多い。電話番号の区切り (3-4 桁) は記憶補助。

実用:
- フォーム項目を**5 個前後**でグループ化
- メニューは**5〜7 項目**
- 段階を増やすときは**進捗を視覚化** (覚えなくていいように)

## ヤコブの法則 (Jakob's Law)

> ユーザーは大半の時間を**他のサイト**で過ごす。だから他サイトと**同じ動作**を期待する。

→ 慣習に従うコスト < 慣習を破るコスト。
新規発明は**それを正当化する強い理由**があるときだけ。

## 親近感の罠 (Mere-Exposure Effect)

人は**馴染みのあるもの**を好む。新しい UI は最初は**不評**で、使うと評価が上がる。

意味:
- リリース直後の批判で**慌てない**
- A/B テストは**学習期間**を含める
- 馴染みのあるパターンは**実は使いやすい**

## ザイオン効果 (Zeigarnik 効果)

> 未完了タスクは完了タスクより記憶に残る。

進捗バーや「あと N 件」表示が効くのはこの効果。
逆に、未完了の通知だらけは**ストレス源**にもなる。

## 直感に反する設計判断

### より少ないオプションが良いことが多い

ジャムの実験 (Iyengar): 24 種類のジャムを並べると 3% 購入、6 種類なら 30% 購入。**選択肢が多いほど決められない**。

### 制約は自由を増やすことがある

完全自由なエディタより、テンプレートのある UI のほうが**書き始められる**。

### 高速なフィードバックが「上手い」を生む

入力 → 即時反応のループは、ユーザーに**自分が制御している**感覚を与える。逆に 500ms の遅延は「下手」感を植え付ける。

→ [[../40-Bridge/Performance-as-UX]]

## モデル変換 (Onboarding)

新規ユーザーは**既存メンタルモデル**で来る。新しい概念をどう導入するか:

- **比較**: 「Trello のカードに似ています」
- **段階開示**: 最初は基本機能だけ、慣れたら高度機能を解放
- **ツアー** (controversial): 押し付けがましく見える、**ニーズ駆動**で出すほうが効く
- **インタラクティブチュートリアル**: 実体験で覚える

→ [[Onboarding-Empty-States]]

## アンチパターン

- 設計者の論理 (DB スキーマ) で UI を組む
- 慣習を理由なく破る
- 全部を教えようとする (ツアー疲れ)
- 「直感的」を盲信して**学習を支援しない**
- 機能名がドメイン特有の専門用語

## チェックリスト

- [ ] 主要メタファが**何か**意識されているか
- [ ] 慣習に従っているか、破るなら**強い理由**があるか
- [ ] Extraneous な負荷を削れているか
- [ ] 主要 CTA が**大きく・近く**配置されているか
- [ ] 新規ユーザーが**最初の成功**を 5 分以内に体験できるか
- [ ] フィードバックが **100ms 以内**に返るか
