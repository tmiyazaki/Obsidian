# インタラクションパターン

## 一行で

> 繰り返し現れる UI 課題への**標準解の語彙**。ゼロから設計するより、**確立された慣習**から逸脱する理由が明確であるべき。

## なぜ重要か

ユーザーは他のアプリで身につけた**期待**を持って来ます。「メニュー三本線」「右上のプロフィールアイコン」「フォーム下の Submit ボタン」… 慣習を破ると、ユーザーは**学習コスト**を支払い、不快感を覚えます。**慣習に乗れない理由**が無いなら、慣習に従うべき。

## ナビゲーション

### グローバルナビゲーション

- **トップバー**: ブランド + 主要メニュー + 検索 + ユーザーメニュー
- **サイドバー**: 階層深いコンテンツ・管理画面
- **ボトムナビ (モバイル)**: 親指の射程内、3〜5 項目
- **ハンバーガー**: 隠すと使われない。**見える数を最大化**してから採用検討

### 局所ナビゲーション

- パンくず: 階層が深いとき
- タブ: 同レベルの**並列**コンテンツ
- ステップ: 順序のあるフロー

## アクション系

### ボタンと優先度

| 優先度 | スタイル | 1 画面あたりの数 |
|---|---|---|
| Primary | 塗り、ブランド色 | **1 個まで** |
| Secondary | 縁取り、塗りなし | 必要数 |
| Tertiary / Ghost | 文字のみ | 多数 OK |
| Destructive | 赤系、確認ダイアログ付き | 必要時 |

Primary が複数あると**選択を強要**される(=何が主なのか見失う)。

### CTA (Call to Action)

- **動詞 + 目的語** で書く: 「保存する」「アカウントを作成」
- 「OK」「送信」だけは抽象的すぎる
- 各画面に**主要 CTA は 1 つ**

### Destructive Actions

- **二段階確認**: 削除ボタン → モーダルで「本当に?」
- 影響範囲を明示: 「このプロジェクトと 42 件のタスクを削除します」
- **取り消し可能性**を示す: 30 秒以内なら Undo、以後不可

## モーダルとオーバーレイ

### Modal (モーダルダイアログ)

ユーザーの注意を**完全に奪う**。使うべきは:
- 重要な確認(削除、課金)
- 短いタスク(別画面に行くほどでもない)

避けるべき:
- 単なる情報通知
- 長文(別ページにすべき)
- 重ねるモーダル(ユーザーは迷子になる)

実装要件:
- ESC で閉じる
- 背景クリックで閉じる(危険な操作以外)
- フォーカストラップ
- 開いたとき**最初のフォーカス可能要素にフォーカス**
- 閉じたとき**呼び出し元にフォーカスを戻す**
- `role="dialog"`, `aria-labelledby`, `aria-modal="true"`

### Toast / Snackbar

短期的な通知。タイムアウトで消える。
- 重要なものは Toast にしない(消えると気づかない)
- 数秒(4〜6s)+ アクション(取り消し等)
- スタックは 3 つまで

### Drawer

スマホで主流。横/下から滑り込む。モーダルとサイドバーの中間。

## フィードバックと状態

### Optimistic UI

サーバー応答を待たず、**成功した前提で**先にUI を更新。失敗したら戻す。
- いいねボタン、お気に入り
- メッセージ送信
- 短いリスト操作

長所: 体感速度が向上。
短所: 失敗時のロールバック設計が必要。

### Loading States(→ [[Loading-States]] 参照)

- 短い (< 300ms): 何もしない(チラつき防止)
- 中 (< 1s): スピナー
- 長 (> 1s): スケルトン or 進捗バー
- 長 (> 10s): 進捗バー必須、キャンセルボタン

### Empty States

「**何もない画面**」は**最も誤解されやすい**:
- 何故空なのかを説明: 「まだ投稿がありません」
- 次の行動を提示: 「最初の投稿を作成」ボタン
- 図やイラストでトーンを和らげる

## 入力支援

### 段階的開示

詳細オプションは**畳んでおいて、必要なら展開**:
```
□ 詳細設定を表示
  ─ 通知頻度
  ─ 言語設定
  ─ ...
```

### Smart Defaults

90% のユーザーが選ぶ値を**初期値**に。「住所をコピー」「名前から請求先を補完」など。

### 入力中バリデーション

- **submit 時のみ**: 古い UX。submit 後にエラー一覧を出すと改修が辛い
- **blur 時に検証**: バランスが良い(離れた瞬間に判定)
- **入力中に検証**: パスワード強度・利用可能名チェックなど即時性が必要なものに限定

### Autofill / Autocomplete

```html
<input autocomplete="email" name="email" />
<input autocomplete="cc-number" name="cardNumber" />
```

ブラウザ・パスワードマネージャの自動入力に乗ることでミス・摩擦が減る。

## ドラッグ & ドロップ

- **ドロップターゲットを視覚化**(枠線、背景色)
- 失敗時は元に戻す
- **キーボード代替**を必ず提供(D&D は身体的・状況的に困難なケースあり)

## 検索

- 入力中のサジェスト
- 直近検索の保存
- フィルタとファセット
- 結果ゼロ時は「もしかして」「条件を緩和」

## 無限スクロール vs ページネーション

| | 無限スクロール | ページネーション |
|---|---|---|
| 探索的閲覧 | ◎ | △ |
| 戻ってくる必要 | △ (位置を見失う) | ◎ |
| フッター到達 | × | ◎ |
| SEO | △ | ◎ |
| 進捗の感覚 | × | ◎ |

ハイブリッド: 「もっと見る」ボタン + 自動読み込み。

## アンチパターン

- 不要なモーダル(別ページで済む内容を奪う)
- Primary ボタン複数(優先順位の崩壊)
- ローディング表示なしの長い待機
- 削除に Undo なし
- フィードバックの遅延(押した感覚が無い)
- ハンバーガー化で**主要ナビが消える**

## チェックリスト

- [ ] 主要 CTA が 1 つに絞れているか
- [ ] 不可逆な操作に Undo or 確認があるか
- [ ] モーダルがアクセシブルか(focus, ESC, aria)
- [ ] ローディング・エラー・空状態が**明示**されているか
- [ ] キーボードのみで完結するか
- [ ] スマホ・タブレットでタップ領域が十分か
