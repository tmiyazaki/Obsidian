# ダッシュボード設計

## 一行で

> ダッシュボードは「**すべてのデータ**」ではなく「**意思決定に必要な信号**」を集約する画面。情報密度より**判断速度**を最大化する。

## なぜ重要か

ダッシュボードは「**よく見られる**」が「**本当に役立っている**」とは限らない。設計が悪いと:
- 数字が並ぶだけで**何を見ればいい**か分からない
- 最初の 1 回見て**二度と開かない**
- 危険なシグナルが**埋もれる**

ダッシュボードは**判断のためのツール**。「眺める美術品」ではない。

## 設計の出発点 — Why?

「**誰が・いつ・何のために**見るか」を決めずに作ると、機能が散漫になる:

```
誰: 営業マネージャ
いつ: 朝 9 時、週 1 回月曜の朝
何のため: チームの今週の見込み確認、危険な案件への介入
```

これが決まると、表示する KPI、更新頻度、必要な深掘り経路が決まる。

## ダッシュボードの 3 タイプ

| タイプ | 目的 | 更新頻度 | 例 |
|---|---|---|---|
| **Strategic** | 経営判断 | 週/月 | 役員ダッシュボード |
| **Analytical** | 探索的分析 | リアルタイム〜日 | データアナリスト |
| **Operational** | 即時介入 | リアルタイム | SRE 監視, コールセンター |

タイプによって**情報密度**と**インタラクション**が変わる。混ぜると失敗。

## 情報階層

→ [[../20-Design/Visual-Hierarchy]]

```
レベル 1: 主要 KPI (大きく、上)
   ↓
レベル 2: 内訳 / トレンド (中)
   ↓
レベル 3: 詳細データ / テーブル (下)
```

ユーザーは**5 秒**でレベル 1 を読み、興味があれば下へ進む。

### F パターン

左上に最重要、右に補足、下にドリルダウン。

## KPI カードの設計

```
┌────────────────────────────┐
│ 今週の売上                   │
│                            │
│ ¥1,234,567                 │  ← メイン値、大
│ ▲ 12% 前週比                │  ← 比較、傾向
│                            │
│ [ 詳細 → ]                  │
└────────────────────────────┘
```

要素:
1. **ラベル**: 何の数値か
2. **数値**: 大きく、桁区切り
3. **比較**: 前期比、目標比 (絶対値だけでは意味薄)
4. **傾向アイコン**: 上昇 / 下降 / 横ばい
5. **時期**: 集計期間
6. **アクション**: ドリルダウン

### 単独の数値は意味薄い

`売上 100 万` だけでは多いか少ないか分からない。
- 前期比、目標比、過去平均との比較を必ず添える
- スパークライン (小さな折れ線) で**直近の流れ**を視覚化

## グラフ選択

→ [[../20-Design/Data-Visualization]]

ダッシュボードでは**ひと目で読める**ことが第一:

| 関係 | 推奨 |
|---|---|
| 推移 | 折れ線、面積 |
| 比較 | 横棒 (3〜10 件) |
| 構成 | スタック棒、ドーナツ (3〜5) |
| 進捗 | プログレスバー、ゲージ |
| 分布 | ヒストグラム |
| 外れ値検出 | 散布図 |

複雑なグラフは**詳細ページへのリンク**にして、ダッシュボードには簡略版を置く。

### グリッドベースの再配置

ユーザーがウィジェットを**並び替え/サイズ変更/追加**できると、自分の業務に合うようにできる。Notion, Datadog, Grafana が代表。

→ [[Settings-Preferences]]

## フィルタとコントロール

ダッシュボード全体に効くフィルタを**上部にスティッキー**:

```
[ 期間: 過去 7 日 ▼ ]   [ チーム: 全員 ▼ ]   [ 通貨: JPY ▼ ]
─────────────────────────────────────────────
... ダッシュボード本体 ...
```

複数ウィジェット連動 = 1 操作で全体が再描画される。

### URL に状態を持つ

→ [[../10-Coding/State-Management]]

```
/dashboard?period=7d&team=all
```

URL コピペで**同じ画面**を共有できる。

## Drill-Down (掘り下げ)

KPI カードや棒のクリックで**詳細ページ**へ:

```
[ 売上 ¥1,234,567 ]
   ↓ クリック
[ 売上詳細 ─ 商品別 / 日別 / 顧客別 ]
   ↓ さらにクリック
[ 個別注文一覧 ]
```

階層は 3 段以内。深すぎると迷子。

## アラート / 異常表示

数値が**閾値を超えたとき**に視覚的に強調:

```
売上目標 達成率
     ███████░░░ 78%      ← 順調 (緑)

エラー率
     ██░░░░░░░░ 5.2%     ← 黄色 (注意)
     ██████████ 12.8%   ← 赤 (警告)
```

色覚多様性に配慮し、**色だけでなくアイコン・数値**も併用。

→ [[../20-Design/Color-Theory]]

## リアルタイム vs 静的

### リアルタイム

- 監視・運用ダッシュボード
- 直近 N 分の数値
- 自動更新 (5 秒〜1 分)
- 接続切断の表示

### 静的

- 経営・分析ダッシュボード
- 日次バッチ更新
- スナップショットで PDF エクスポート

過剰なリアルタイムは**コスト**(計算・帯域)と**集中阻害**を生む。本当に必要か問う。

## エクスポートと共有

- **画像 / PDF** で報告書化
- **CSV** で生データ
- **URL 共有** (フィルタ込み)
- **スケジュール送信** (毎週月曜にメール)

ダッシュボードで終わらせず、**他人に届ける**機能を含めると価値が広がる。

## 状態管理

→ [[Loading-States]]

ダッシュボードは多数のウィジェットが並ぶため:

- **個別**にローディング (全部待たない)
- **個別**にエラー (1 つ落ちても他は動く)
- ウィジェットが**遅い**ことを表示 (`Loading…`)
- 失敗したウィジェットだけ再試行可能

## パフォーマンス

→ [[../10-Coding/Performance]] / [[../40-Bridge/Performance-as-UX]]

- 初期描画は**軽いウィジェット**から
- 重いクエリは**並列実行 + キャッシュ**
- 仮想化 (大量行のテーブル)
- Materialized View / OLAP DB の活用

ダッシュボードの遅さは「使われなくなる」直接原因。

## モバイル対応

ダッシュボードは情報密度が高く、モバイルでは破綻しがち:
- 主要 KPI **3〜5 個**だけ縦スタック
- 詳細グラフは**横スクロール**または**省略**
- フィルタは**ボトムシート**へ
- 必要なら**モバイル専用ビュー**を別途設計

## アクセシビリティ

→ [[Accessibility]]

- グラフに**データテーブル代替**
- 色だけで意味を伝えない
- KPI 数値の**変化**は `aria-live` で通知
- 数値ジャンプ時の**警告音**を OFF にできる

## アンチパターン

- 「全部入り」ダッシュボード(20 ウィジェットで何も見えない)
- 単独数値だけで**比較なし**
- 全部リアルタイムで**毎秒チラつく**
- 凡例がグラフから**離れている**
- 円グラフで 8 要素を比較
- フィルタ変更で**全リロード** (体感悪)
- 印刷したら**真っ黒**(ダーク前提でライト未対応)

## チェックリスト

- [ ] 「**誰が・いつ・何のため**」が定義されているか
- [ ] **5 秒**で主要メッセージが伝わるか
- [ ] KPI に**比較**(前期比・目標比)があるか
- [ ] フィルタ状態が**URL に**保持されるか
- [ ] ウィジェットが**個別にロード/エラー**できるか
- [ ] モバイル表示で**主要 KPI** が読めるか
- [ ] 色覚多様性 + アイコン併用か
- [ ] 印刷 / PDF エクスポートで読めるか
