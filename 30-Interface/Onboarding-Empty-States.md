# オンボーディングと空状態

## 一行で

> 新規ユーザーの**最初の 5 分**で離脱の半分が決まる。空状態は「**何もない**」ではなく「**最初の一歩**」の場所。

## なぜ重要か

機能の充実より、**最初の成功体験 (First Time User Experience, FTUE)** が定着率を決めます。「こんなことができそう」と感じさせ、「実際にできた」を体験させる ── ここを設計しないと、機能がいくらあっても刺さりません。

空状態は新規ユーザーが**最初に出会う画面**。「データがない」と表示するだけは機会損失。

## オンボーディングの段階

```
┌──────────┐  ┌────────────┐  ┌──────────┐  ┌─────────┐
│ Sign up  │→ │ First value│→ │ Habit    │→ │ Mastery │
└──────────┘  └────────────┘  └──────────┘  └─────────┘
```

- **Sign up**: 摩擦最小化、価値の予告
- **First value**: 「**Aha! moment**」 ─ ユーザーが「これは良い」と気づく瞬間
- **Habit**: 繰り返し利用、習慣化
- **Mastery**: 高度機能の習得

最も重要なのは **First value までの時間 (Time-to-Value)**。これを**短く、確実に**届かせる。

## オンボーディングの設計

### 1. 必要最小情報で始める

サインアップ時に**全部の情報**を集めない。**触らせてから**徐々に。

```
❌ 登録時: 名前 + メール + 会社名 + 役職 + 業種 + 規模 + 関心 + パスワード
✅ 登録時: メール + パスワード
   後で: チュートリアル中・初操作時に随時
```

### 2. 「動かすこと」より「成功すること」

ツアーで全機能を案内するより、**1 つだけ**成功体験を作る。
- ToDo アプリ: 「最初のタスクを追加してみましょう」
- 写真アプリ: 「写真を 1 枚アップロード」
- メモアプリ: 「最初のメモを書いてみましょう」

### 3. プログレッシブオンボーディング

機能を**使う直前**に教える (Just-in-Time):

```
ファイル共有機能を初めて使う時 → ここで簡潔な説明
公開設定を初めて変える時 → 簡単なコーチマーク
```

「最初に全部教えるツアー」は**忘れられる**。**必要なときに**出すと刺さる。

### 4. 進捗の可視化

```
[●●●○○] あと 2 ステップで完了
```

完了感が次のステップを促す (ザイガルニク効果)。

### 5. スキップ可能

**いつでもスキップ可能**にする。押し付けがましいツアーは離脱を早める。

### 6. 既定値で動く状態を提供

ユーザーが何も設定しなくても**動くサンプル**を提供:
- サンプルプロジェクト
- サンプルデータ
- テンプレート

「真っ白なキャンバス」より「**少し書かれた紙**」のほうが書き始められる。

## 空状態 (Empty State) の設計

「**何もない**」状態は**バグなのか正常なのか**で混乱を生む。最低限:

### 1. 状態の説明

```
✅ まだプロジェクトがありません
✅ 検索条件に一致するアイテムが見つかりませんでした
```

### 2. 次の行動

```
[ プロジェクトを作成 ]
または [ サンプルから始める ]
```

### 3. トーン

過度に祝祭的でなく、過度に冷たくもなく。**少し励ます**くらいが適切:

```
✅ プロジェクトを作って、最初のアイデアを形にしましょう。
```

### 4. ビジュアル

シンプルなイラストを置くと**温度**が出る。ただし「装飾だけ」になりがち ── アクションを優先。

## 空状態の 4 種

### 1. First Use (初回)

ユーザーがまだ何もしていない状態。**最初の一歩**を促す。

### 2. User Cleared (空にした)

完了したり削除した結果。「すべて完了!」のような肯定的フィードバック。

### 3. No Results (検索結果ゼロ)

「見つかりませんでした」+ 条件緩和の提案:

```
"プロジェクト管理" の結果がありません

もしかして:
  • キーワードを減らす
  • フィルタをリセット [ リセット ]
```

### 4. Errors (失敗)

→ [[Loading-States]]、[[../10-Coding/Error-Handling]]

「何が起きて、何ができるか」。

## チェックリスト・チュートリアルのパターン

### コーチマーク

ハイライト + 吹き出しで指す。
- 1 度に 1 つ
- 閉じるオプション必須
- 文字は短く (10〜15 字)

### スポットライト

画面の一部以外を暗くし、注目を集める。
- 強い手段なので**重要時のみ**
- ユーザーの操作を**ブロック**する場合は「次へ」を明示

### Inline Hints

UI の中に**小さなヒント**を埋め込む。

```
[ + 新規作成 ]  ← ここから始めましょう
```

操作対象の隣に置くのが効く。

### Empty State as Tutorial

空状態自体を**ガイド**にする (これが最も効果的なケースが多い):

```
┌────────────────────────────────────┐
│  📋 まだタスクがありません           │
│                                    │
│  上のボタンから最初のタスクを追加 →  │
│                                    │
│  または [ サンプルを試す ]           │
└────────────────────────────────────┘
```

## A/B テストとオンボーディング

オンボーディングは**改善のレバレッジが大きい**。
- ステップ数を変える
- 必須項目を減らす
- サンプルデータの有無
- 誘導文の語調

ただし、**短期コンバージョンと長期定着**は別物。両方測る。

→ [[User-Research]]

## 既存ユーザーへの再オンボーディング

新機能リリース時:

- 重要なら**ライト版ツアー** (1〜3 ステップ)
- 通常は **What's new** モーダル(押し付けない)
- バッジ通知 + 場所への誘導

「全員強制ツアー」は離脱を呼ぶ。**選択肢**として置く。

## アンチパターン

- 起動時に**長いツアー**で全機能解説
- スキップボタンが**目立たない**
- メアド確認**ループ** (確認しないと使えない、確認メールが届かない)
- 空状態が「No data」だけ
- サインアップ時に**全情報**を集める
- 初回起動でいきなり**通知許諾・位置情報**ダイアログ
- サンプルデータが**消せない**

## チェックリスト

- [ ] First value までの**時間**が短いか (< 5 分)
- [ ] サインアップが**最小情報**で完了するか
- [ ] 空状態が**次の行動**を案内しているか
- [ ] チュートリアルは**スキップ可能**か
- [ ] 重要な機能は**Just-in-Time** で案内されるか
- [ ] サンプルデータ・テンプレートで「触れる」状態か
- [ ] 失敗パス (確認メールが来ない等) も設計されているか
