# ユーザーリサーチ

## 一行で

> リサーチは「**意見を集める**」ことではない。**ユーザーの行動・文脈・困りごと**を観察し、**作るべきものの仮説を検証**する活動。

## なぜ重要か

「ユーザーが欲しいと言ったもの」と「**実際に使うもの**」はしばしば違います (Henry Ford のとされる「速い馬」逸話)。リサーチをスキップすると:
- 自分の思い込みで作って **誰にも刺さらない**
- 細かい改善ばかりで **大きな問題**に気づかない
- 機能議論の根拠が**声の大きい人**になる

リサーチは**確実性を上げ、後戻りを減らす**投資です。

## リサーチの軸

### 何を知りたいか × どう調べるか

|  | 行動 (What) | 動機・理由 (Why) |
|---|---|---|
| **質的** | ユーザビリティテスト、観察 | インタビュー、日記研究 |
| **量的** | 解析、A/B テスト | アンケート、サーベイ |

- **質的**: 少人数 (5〜8 名) 、深い理解、**なぜ**が分かる
- **量的**: 多人数、統計的傾向、**どれくらい**が分かる

両者は**競合せず補完**する。質的で仮説を立て、量的で検証。

## 調査手法 (主要)

### 1. ユーザビリティテスト

- 5 ユーザーで主要問題の 80% が見つかる (Nielsen)
- タスクを与え、**話しながら**操作してもらう (Think Aloud)
- リモート可 (Maze, UserTesting, Useberry)
- **何ができないか**を発見する手段

### 2. インタビュー

- 30〜60 分、半構造化 (核質問 + フォロー)
- **オープン質問** ("どうやって…?") を中心に
- 「なぜ?」を 5 回掘り下げる
- 5〜8 人で**飽和** (新しい発見が減る) する目安

### 3. 観察 / コンテクスチュアルインクワイアリ

実際の利用環境で**作業を観察**。インタビューで言語化されない**暗黙の手順**が見える。
B2B SaaS、業務システムで特に有効。

### 4. アンケート

母集団を測る。**少数の選択肢 + 自由記述少々**。質問数を絞る (10 問以内)。
NPS、CSAT、SUS (System Usability Scale) など標準尺度を活用。

### 5. 解析データ (Quantitative)

- ファネル分析
- ヒートマップ (Hotjar, Microsoft Clarity)
- セッションリプレイ
- 機能利用率

「**何が起きているか**」は答えられるが「**なぜか**」は答えない。質的調査と組み合わせる。

### 6. A/B テスト

仮説 → ランダム割付 → 統計検定。
- 効果サイズと検出力を**事前**に決める
- p-hacking を避ける (期間・指標を固定)
- 局所最適に陥る (大きな変化は A/B では出にくい)

### 7. カードソート / ツリーテスト

→ [[Information-Architecture]]

ナビ構造の妥当性を実装前に検証。

### 8. 日記研究

数日〜数週間、ユーザーが自身の利用を**日々記録**。長期スパン・文脈依存の理解に。

## ダブルダイヤモンド

```
┌───────────┐   ┌───────────┐
│ Discover  │ → │ Define    │  問題を理解する
└───────────┘   └───────────┘
      ↓               ↓
┌───────────┐   ┌───────────┐
│ Develop   │ → │ Deliver   │  解を作って届ける
└───────────┘   └───────────┘
```

- **Discover**: 広く調査 (発散)
- **Define**: 問題を絞る (収束)
- **Develop**: 解を広げる (発散)
- **Deliver**: 解を選ぶ (収束)

リサーチは Discover/Develop で**特に**重要。

## 質問の仕方

### 良い質問

- 「最後に X したのはいつですか?」(過去事実 = 信頼できる)
- 「そのとき何をしていましたか?」(文脈)
- 「なぜそうしたのですか?」(動機)
- 「他にどんな方法を試しましたか?」(代替案)

### 悪い質問

- 「もし X があったら使いますか?」(将来の予測は不正確)
- 「これ、いいと思いますか?」(バイアス、人は肯定的に答えがち)
- 「なぜ X しないのですか?」(防衛的反応)

→ ユーザーは**未来の自分の行動を予測できない**。**過去の行動**を聞く。

## バイアスを避ける

### 確証バイアス

「機能 X が刺さるはず」と思っているとそう聞こえる。
対策: 仮説を**反証する**質問も用意。「使わなかった理由」を聞く。

### モデレーターバイアス

進行役の口調が回答を誘導:
- 「これ、わかりやすいですよね?」← 誘導
- 「これを見て、何だと思いますか?」← 中立

### サンプルバイアス

熱心なユーザーばかり集めると、**離脱層の声**が抜ける。

### 思い起こしバイアス

「過去 1 ヶ月で何回?」より「最後に使ったのはいつ?」の方が正確。

## ペルソナ vs JTBD

### ペルソナ

「30 代女性、エンジニア、東京在住」のような**人物像**。
落とし穴: ステレオタイプ化、属性で行動を予測できない。

### Jobs to Be Done (JTBD)

「**ユーザーが何かを雇う**ときの状況・動機・期待」を中核に置く:

```
状況: 朝の通勤中、片手スマホ
動機: 短時間で重要ニュースだけ把握したい
期待: 主要 5 件を 3 分で
雇う対象: ニュースアプリ
代替候補: Twitter スクロール
```

属性ではなく**状況**で考えると、機能優先度がはっきりする。

## リサーチを習慣化する

### 量より頻度

四半期に 1 度の大型より、**毎月小さく**。
- 週 1 回 30 分のユーザビリティテスト
- リリース前の 5 ユーザー検証

### 共有

レポートは長文でなく:
- **動画クリップ** (痛い瞬間 30 秒) で議論を変えられる
- **3 つの主要発見** + 推奨アクション
- 関係者を**観察に同席**させる(レポートより 10 倍効く)

### Repository

過去のリサーチを Notion/Dovetail などに集約。「これ、半年前に分かってた」を防ぐ。

## アンチパターン

- リサーチ = アンケート、と思い込み (行動が見えない)
- 「思いますか?」だらけ
- リサーチ後に**何も決まらない**
- 結果が**自説の補強**にだけ使われる
- 5 人で十分なのに 50 人を調査して**進まない**
- レポートが長文・図で**誰も読まない**

## チェックリスト

- [ ] 何の**仮説を検証**するか明確か
- [ ] 質問が**過去の行動**ベースか
- [ ] バイアス (誘導・確証) を意識しているか
- [ ] 結果が**意思決定**に繋がるか
- [ ] 関係者が**観察に同席**したか
- [ ] 発見が**Repository に蓄積**されているか
