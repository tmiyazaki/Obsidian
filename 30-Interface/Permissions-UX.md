# 権限 UX (Permissions)

## 一行で

> 権限 UX は「**誰が・何を・どの範囲で**できるかを、ユーザーが**理解・予測・調整できる**形で提示する」設計。複雑なアクセス制御を**直感的に**運ぶ。

## なぜ重要か

権限は誤用すると:
- 機密情報の**漏洩**
- 重要データの**誤削除**
- ユーザーが「**できないはずのこと**ができてしまう / **できるはずのこと**ができない」混乱

良い権限 UX は安全性と生産性を両立します。逆に悪いと、ユーザーは「**全員 Admin**」にして崩壊する。

## 権限モデル

→ [[../10-Coding/Security#認可設計]]

### RBAC (Role-Based)

```
Owner / Admin / Editor / Viewer
```

学習が容易、設定が簡単。中小規模に向く。

### ABAC (Attribute-Based)

```
属性 (部署、地位、勤務時間、地域) で動的判定
```

複雑だが柔軟。エンタープライズ。

### ReBAC (Relation-Based)

```
ユーザー → リソース の関係グラフで判定
```

Google Drive, Notion 型。「このフォルダのメンバーはこのファイルを見られる」のような関係駆動。

実プロダクトは複数を組み合わせる。

## 共有 UI の典型

### Google Docs 型

```
[ ファイルを共有 ]
─────────────────────────────────
名前またはメールアドレス: [_________]
権限: [ 編集者 ▼ ]   [招待を送信]
─────────────────────────────────
このファイルにアクセスできる人:
  Alice (オーナー)              編集
  Bob                          編集 ▼
  Carol                        閲覧 ▼  [削除]
─────────────────────────────────
リンクを知っている全員: [ アクセス制限あり ▼ ]
─────────────────────────────────
[ リンクをコピー ]              [ 完了 ]
```

要素:
- **個別招待** (メール/ID)
- **権限選択** (招待時)
- **既存メンバー一覧** + 編集/削除
- **リンク共有** (公開範囲)
- **コピー可能なリンク**

### Notion / Slack 型

ワークスペース → スペース → ドキュメントの**継承**:

```
[ 親フォルダから継承: ✓ ]
   ↓ チェック外すと個別設定
[ 個別設定 ]
  Alice  - 編集可
  Team A - 閲覧可
```

継承を**視覚的に**示すと迷わない。

## 権限の表記

「**何ができるか**」を平易に:

| 内部表記 | UI 表記 |
|---|---|
| `read` | 閲覧者 (Viewer) |
| `comment` | コメント可 |
| `write` / `edit` | 編集者 (Editor) |
| `admin` | 管理者 |
| `owner` | オーナー |

権限名は**動詞 + ロール**ではなく**ロール名**で。`「Can Edit」「Can View」`のような自然な英語表現も多い。

## ロールの説明

設定画面で**各ロールが何をできるか**を表で示す:

```
              Viewer  Editor  Admin  Owner
コメント         ✓      ✓       ✓      ✓
編集            -      ✓       ✓      ✓
共有            -      -       ✓      ✓
削除            -      -       ✓      ✓
オーナー譲渡    -      -       -      ✓
```

「コメントできる人を増やしたい」と思ったとき、Editor を割り振らずに済む。

## 権限の**透明性**

「**今、誰が見れる**」が一目で分かるべき:

- 共有アイコン (鍵 / 公開 / 限定)
- 「このページは Public」のラベル
- ヘッダに参加者アバター → クリックで一覧

```
[ 🌐 公開 - リンクを知る誰でも閲覧可 ]
[ 🔒 制限あり - 招待された 5 名のみ ]
[ 🌍 ワークスペース全員 ]
```

意図せず公開設定にしている**事故防止**。

## 操作の事前判定 vs 事後通知

### 事前判定 (推奨)

権限がない操作は**ボタンを無効化** + ツールチップで理由:

```
[ 削除 ] (無効)
   "削除には Admin 権限が必要です"
```

### 事後通知 (避ける)

操作試みた後にエラー:
```
"権限がありません" ← フォームを書き終わってから言われると最悪
```

「**なぜ無効か**」が見えれば、ユーザーは権限申請のアクションを取れる。

## 権限申請フロー

```
[ このファイルは閲覧専用です ]
[ 編集権限をリクエスト ]
   ↓
[ オーナーに通知 ]
   ↓
[ 承認 / 拒否 ]
   ↓
[ ユーザーに結果通知 ]
```

ブロッキングなく協働できる仕組み。Google Docs の「アクセスをリクエスト」が好例。

## 権限の継承と上書き

階層構造で:
- **継承**: 親の権限が子に伝わる
- **上書き**: 子で個別設定可

UI で:
- 「**親から継承**」のチェックボックス
- 上書き中の権限は**色やアイコン**で強調

```
このフォルダ (継承)
├─ ファイル A (継承)
├─ ファイル B (継承)
└─ ファイル C (個別設定: Alice のみ)  ⓘ
```

## オーナー譲渡

オーナー = 最強権限。1 リソースに 1 名が原則。

譲渡フロー:
1. 既存オーナーが譲渡先を選ぶ
2. 譲渡先がメール/通知で**承認**
3. 旧オーナーは**Admin に降格** or 退去

退職処理で**オーナー孤立**(永遠にロック)を防ぐ。

## 退会処理

メンバーが退会した場合:
- 所有リソース = どうなる? (孤立? 自動譲渡?)
- 共有リソースから**自動除外**
- 監査ログに**退会前の活動**を保持

設計しておかないと、退会後に**オーナー不在のフォルダ**が残る。

## 権限ログと監査

「**誰が・いつ・何を・誰に対して**」変更したか:

```
2026-05-01 10:23 - Bob が Carol を編集者として追加
2026-05-01 10:24 - Alice が公開リンクを生成
2026-05-02 09:00 - Bob が David をオーナーに譲渡
```

セキュリティインシデント時に必須。Enterprise プラン機能の主要要素。

## グループ・チーム

個別ユーザーへの権限付与は**スケールしない**:

```
[ Engineering チーム ] - 編集者
[ Marketing チーム ]  - 閲覧者
[ Alice ]             - 個別追加: 編集者
```

グループに権限を当て、メンバー追加でスケール。

## 公開リンク (Share Link)

```
[ リンクを知る全員 ]
  ☐ 閲覧可能
  ☐ コメント可能
  ☐ 編集可能
  ☐ 期限を設定: [ 7 日後 ▼ ]
  ☐ パスワード保護: [ ___ ]
[ リンクをコピー ]
```

考慮:
- **期限切れ**で自動失効
- **失効** / 再生成
- ダウンロード/印刷の制御
- ログインを要求するか

## アクセシビリティ

- 権限選択ドロップダウンは**十分な説明**(`aria-describedby`)
- 状態アイコンに**テキスト併記**
- 危険な権限変更には**確認ダイアログ**

→ [[Accessibility]]

## アンチパターン

- 全員 Admin (権限が機能していない)
- 権限名が**技術用語**(`READ_WRITE_DELETE`)
- 公開設定が**気付かないうちに**変わる
- 個別ユーザーに権限が**散在**してメンテ不能
- 権限なし操作で**サーバエラー**(事前無効化なし)
- 退会処理で**オーナー消失**
- 監査ログ**なし**(誰が変えたか追えない)

## チェックリスト

- [ ] **共有状態**(誰が見れるか)が画面上で見えるか
- [ ] 権限名が**ユーザーの言葉**か
- [ ] 権限なし操作は**事前無効化**されているか
- [ ] 公開リンクに**期限・パスワード・取消**があるか
- [ ] 監査ログがあるか
- [ ] グループ/チーム単位で権限を割り当てられるか
- [ ] 退会・譲渡フローが設計されているか
