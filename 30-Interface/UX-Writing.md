# UX ライティング

## 一行で

> UX ライティングは「**画面に出る言葉**」の設計。文章ではなく**インターフェースの一部**として、一語一語が機能を持つ。

## なぜ重要か

ボタンラベル、エラーメッセージ、空状態、ツールチップ ── ユーザーが「**読まずに分かる**」UI はほぼ存在しません。文言が UI の理解を決め、行動を誘導し、信頼を築く(あるいは壊す)。同じデザインでも文言だけで**コンバージョン率が倍**になる例は珍しくない。

## 4 つの基本原則 (Voice & Tone)

### 1. Clear (明瞭)

専門用語・技術用語を避ける。**ユーザーの語彙**で書く。

```
❌ 認証エラー: トークンが失効しました
✅ ログインの有効期限が切れました。再度ログインしてください。
```

### 2. Concise (簡潔)

**削れる言葉は削る**。読みやすさは情報量ではなく**ノイズの少なさ**で決まる。

```
❌ 申し訳ございませんが、お客様のリクエストを処理することができませんでした
✅ 処理に失敗しました
```

### 3. Useful (役立つ)

各文言が**次の行動**を示すか問う。

```
❌ 「エラーが発生しました」 (何をすればいい?)
✅ 「保存に失敗しました。もう一度お試しください。」
```

### 4. Consistent (一貫)

同じものを**同じ呼び方**で。`サインイン` と `ログイン` を混在させない。

→ [[../40-Bridge/Naming-as-Design]]

## ボイスとトーンの違い

- **ボイス (Voice)**: ブランドの**人格**。常に一定。例: 親しみ・信頼・専門
- **トーン (Tone)**: 状況に応じて変わる**温度**。エラー時は丁寧、成功時は軽快、決済時は慎重

```
ボイス: 親しみのある専門家
  └ 通常時: 「いつでもご相談ください」
  └ エラー時: 「うまくいきませんでした。一緒に解決しましょう」
  └ 決済時: 「お支払い前に内容をご確認ください」
```

## 文言タイプ別の指針

### ボタン (CTA)

- **動詞 + 目的語**: 「保存する」「アカウントを作成」
- 「OK」「送信」は曖昧 → 何が起きるか具体に
- 危険な操作は明示: 「削除」より「**永久に削除**」

### エラーメッセージ

3 要素を含める:
1. **何が** 起きたか
2. **なぜ** (任意、ユーザーが理解できる範囲で)
3. **どう直すか**

```
❌ Error 422
✅ メールアドレスの形式が正しくありません。
   「name@example.com」のように @ を含めて入力してください。
```

ユーザーを責める表現を避ける:

```
❌ あなたの入力は無効です
✅ 数字のみ入力してください
```

### 空状態

→ [[Onboarding-Empty-States]]

ただ「**データなし**」は最悪。

```
✅ まだプロジェクトがありません。
   最初のプロジェクトを作成して、チームと共有しましょう。
   [プロジェクトを作成]
```

### 確認ダイアログ

タイトル = 行動、本文 = 影響、ボタン = 次の行動

```
タイトル: このプロジェクトを削除しますか?
本文: 42 件のタスクと添付ファイルもすべて削除されます。この操作は取り消せません。
ボタン: [キャンセル]  [プロジェクトを削除]
```

ボタンが「OK」「Cancel」だけだと、押してから不安になる。**ボタンに動作を書く**。

### ローディング

「Loading...」より:

```
✅ 計算しています…  (何が起きているか)
✅ あと数秒…       (見通し)
```

### 成功メッセージ

過度に祝福しない。「**何が起きたか**」を簡潔に。

```
✅ 保存しました
✅ メールを送信しました (3 名)
```

## マイクロコピーで離脱を防ぐ

### フォームのヒント

```
[ パスワード ___________ ]
8 文字以上、英数字を含む  ← 入力前に伝える
```

送信失敗で初めて知るのは×。**事前に**期待を伝える。

### サブミットボタン横の安心材料

```
[ アカウントを作成 ]
クレジットカード不要・いつでも解約可
```

決済・登録の不安を**ボタンの直前/直後**で和らげる。

### プレースホルダ ≠ ラベル

プレースホルダは入力中に消える → 思い出せない。**ラベルは別途上に固定**。

→ [[Forms-and-Input]]

## 国際化を見据えた書き方

→ [[../40-Bridge/Internationalization]]

- **文の組み立て直し**を避ける (`{name} さんがログインしました` のような語順依存)
- 略語を避ける (翻訳が困難)
- 文字数の **30〜40% 増**を見込む (英→独、英→日)
- アイコンに依存しない言葉

## ライティング QA プロセス

### 1. 5 秒テスト

5 秒だけ見せて、**何ができるか**伝わるか質問。

### 2. 声に出して読む

不自然な硬さ、長い修飾、繰り返しが**音で**分かる。

### 3. 削れる単語を消す

「申し訳ございませんが」「お手数ですが」「お客様の」 ── 機能を持っていない言葉は削る。

### 4. 動詞を強くする

```
❌ 設定の変更を行う
✅ 設定を変更する
```

### 5. 読み手の言葉に変える

「ユーザビリティテスト」を実施し、**ユーザーが詰まる用語**を発見する。

→ [[User-Research]]

## アクセシビリティ

- スクリーンリーダーで**読み上げて自然**な順序
- 略語は最初に展開: `WCAG (Web Content Accessibility Guidelines)`
- リンクテキストは**それ単体で意味**: 「こちら」より「ヘルプを見る」
- アクション動詞は**主語が省略可能**だが、文脈で迷うなら補う

## 文言の正本管理

文言を**コードに直書きしない**:

```ts
// ❌ 直書き
<button>保存する</button>

// ✅ 翻訳キー経由
<button>{t("action.save")}</button>
```

理由:
- 国際化対応が後付けで効く
- 文言変更が**コード変更なし**で可能
- ライティング担当者が触れる
- 一貫性が保ちやすい

## アンチパターン

- 「OK」「Cancel」「Submit」だらけ
- システム用語の漏れ (`HTTP 500`, `null`, `undefined`)
- ユーザーを責める文体
- 専門用語の説明なし
- ジョーク・カジュアルすぎ (深刻な操作で不適切)
- 全文を太字・全文を CAPS
- 同じ概念に**複数の呼び方**

## チェックリスト

- [ ] 各画面の文言が**5 秒**で伝わるか
- [ ] エラーは「何が・どう直すか」を伝えているか
- [ ] 同じものを**同じ呼び方**で呼んでいるか
- [ ] ボタンに**動詞 + 目的語**で具体的に書かれているか
- [ ] 削れる単語が削られているか
- [ ] 翻訳キー経由で管理されているか
