# リアルタイム協働 (Multiplayer UX)

## 一行で

> 同じ画面に複数の意識が共存する設計。「**他者の存在**」が見え、「**競合**」が解消され、「**履歴**」が辿れる。

## なぜ重要か

Figma, Notion, Google Docs, Linear ── 現代のプロダクティビティ製品はほぼすべて多人数同時編集が標準です。シングルユーザー前提で作ったあとに後付けすると、データモデル・UI・サーバ全層を書き直すことになる。最初から見越した設計が必要です。

## マルチプレイヤーが要求する 4 軸

### 1. Presence (存在)

「**今ここに誰がいる**」が見える:
- 顔写真の集まり (ヘッダ、サイドバー)
- カーソルの色つき名前
- 編集中フィールドのハイライト
- ステータス (オンライン / 離席 / 集中モード)

カーソル追従はライブ感を生むが、**100ms 以下のレイテンシ**でないとイライラする。

### 2. Awareness (気づき)

「**他者が今何をしているか**」:
- リアルタイム入力 (文字が次々現れる)
- カーソル位置
- 選択範囲の色付き表示
- 「Alice が編集中…」のラベル

過剰だと**気が散る**。設定で**他者表示を抑制**できると親切。

### 3. Conflict Resolution (競合解消)

2 人が同じ文字を同時編集したらどうする?

#### ロック方式 (Pessimistic)

「Alice が編集中なので待ってください」
- 古典的、安全
- ストレス源(待たされる)
- 段落単位ロックなら現実解

#### 楽観的同時編集 + マージ (CRDT / OT)

両方を受け入れて自動解消:
- **OT** (Operational Transformation): Google Docs
- **CRDT** (Conflict-free Replicated Data Type): Figma, Notion, Linear

CRDT はオフライン編集にも強く、現代の主流。Yjs, Automerge が代表ライブラリ。

### 4. History (履歴)

「**何が・誰が・いつ**変更したか」:
- 変更履歴ビュー
- 行ごとの最終編集者 (`git blame` 風)
- 過去のスナップショット (時間遡行)
- Undo / Redo (個人 vs 共有)

## アーキテクチャの選択肢

### WebSocket

双方向、低レイテンシ。チャット、共同編集の標準。

### Server-Sent Events (SSE)

サーバ → クライアントの一方向。ストリーミングに適す。

### WebRTC

P2P、超低レイテンシ。ビデオ通話、ホワイトボード。

### Polling

最後の手段。インフラ制約があるとき。

### Realtime プラットフォーム

- **Liveblocks**: コラボ機能を SDK で提供
- **Supabase Realtime**: Postgres の変更を購読
- **Pusher / Ably**: WebSocket as a Service
- **PartyKit**: エッジで動く WebSocket

自作より既存を使うほうが遥かに速く・安定。

## CRDT の基礎

CRDT は「**どんな順序で操作が届いても同じ結果になる**」データ構造:

- **G-Counter**: 単調増加カウンタ
- **LWW-Register**: 最後の書き込み勝ち (タイムスタンプベース)
- **OR-Set**: 追加・削除を扱える集合
- **RGA / Yata**: テキスト編集

実装は Yjs, Automerge, Loro が成熟している。

CRDT の利点:
- **マージが自動**(コンフリクトなし)
- **オフライン編集**可能
- ローカルファースト思想と相性

## オフラインファースト

ネットワークが切れても動き、復活時に同期:

1. ローカルにすべて書く (IndexedDB / SQLite)
2. オペレーション (CRDT updates) をキューイング
3. 接続復活時に**サーバと同期**
4. 競合は CRDT が解消

→ Local-first ソフトウェア (Ink & Switch のマニフェスト)

## UX 上の課題と解

### 自分のカーソルが**飛ぶ**

サーバ更新が来て、テキストが動くと**カーソルが意図しない場所**へ。
解: カーソル位置を**論理ポインタ** (前後の文字 ID) で表現。テキストが増減してもアンカー追従。

### 他人の編集が**邪魔**

他人が同じ段落を編集中、自分が間違えて上書きする恐怖。
解: 編集中の段落に**色付き枠**、Lock を**柔らかく**示す。

### Undo の意味

自分の Undo は**自分の操作**だけ取り消す? 全員の操作?
解: 通常は**自分の操作だけ**Undo。「全員の最後の変更」は明示的に「履歴から復元」で。

### 通知の洪水

10 人が同時編集中、変更通知を全部出すとうるさい。
解: **集約**(「3 人が編集中」)、**フォロー機能**(特定の人の動きだけ追う)。

## コミュニケーション機能

### 1. コメントとアノテーション

- 行 / 図形 / 範囲に紐付く
- スレッド化
- 解決 (Resolve) で畳む
- メンション (@user) → [[Notifications]]

### 2. リアクション (絵文字)

軽い同意・反応の手段。会話を増やさず温度を伝える。

### 3. ボイス・ビデオ統合

Figma の "Audio chat" のように、画面操作と通話を一体化。

### 4. ライブ vs 非同期

- **ライブ**: 同時に編集
- **非同期**: 別時間に編集 + コメント

両方支援するのが現代的。Loom (動画) の埋め込みで非同期説明。

## 権限とロール

→ [[Permissions-UX]]

- Viewer / Commenter / Editor / Owner
- 招待リンク (権限指定)
- リンク共有 vs 個別招待
- 共有範囲の**可視化**(誰が見れるか一目)

## パフォーマンス

- 操作を**バッチ化**(50ms ごとに送信)
- 大量更新時の**スロットリング**
- 接続復帰時の**差分同期**
- ファイル巨大化時の**ページング**(全体を一度に同期しない)

→ [[../10-Coding/Performance]] / [[../10-Coding/Concurrency-Async]]

## 信頼性

- 接続切断の**サイレントリカバリ**(自動再接続)
- 状態の**接続バッジ** (✓ Connected / ⚠ Reconnecting / ✗ Offline)
- 失敗した操作の**保存先**(復活時送信)

## アクセシビリティ

- 他者カーソル / 編集を SR で**煩く読み上げない**(`aria-live="off"` で適切に抑制)
- 重要な通知は通常の通知パターンに乗せる
- カーソル色は**色覚多様性**に配慮 + 名前ラベル併記

→ [[Accessibility]]

## アンチパターン

- ロックで**待たされる**コラボ
- カーソル多数で**重く**なる
- 履歴がなく「**誰が壊した**」が分からない
- 自分の Undo で**他人の作業まで消える**
- オフラインで作業して**復活時にすべて喪失**
- 通知洪水で重要なメンションが埋もれる

## チェックリスト

- [ ] **Presence** (誰がいるか) が見えるか
- [ ] **競合解消**戦略 (CRDT/OT/Lock) が決まっているか
- [ ] 接続状態が**ステータス**で見えるか
- [ ] **履歴**が辿れるか (誰が・いつ・何を)
- [ ] オフライン → オンライン復帰で**整合**するか
- [ ] 他者編集の**通知が過剰でない**か
- [ ] アクセシビリティで**煩くない**か
