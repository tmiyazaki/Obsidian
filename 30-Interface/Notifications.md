# 通知システム設計

## 一行で

> 通知は「**ユーザーの注意を借りる**借金」。返せる価値があるときだけ送り、利息(離脱)を払わない設計をする。

## なぜ重要か

通知が役立てばユーザーは戻ってきます。雑な通知は:
- 通知 OFF → 重要なものも届かなくなる
- アプリ削除
- ブランドへの不信

通知設計は **コミュニケーション設計**であり、UX の最も延長戦的な接点。

## チャネルの整理

| チャネル | 即時性 | 介入度 | 主な用途 |
|---|---|---|---|
| **Toast / Snackbar** | 即時 | 弱 | 操作直後のフィードバック |
| **インアプリ通知** | アプリ内のみ | 中 | コラボ・更新 |
| **バナー / アラート** | 即時 | 強 | 緊急 (障害、メンテ) |
| **プッシュ通知** | OS レベル | 強 | アプリ外でも届く重要事項 |
| **メール** | 非同期 | 弱 | 記録に残す、長文 |
| **SMS** | 非同期 | 強 | OTP、緊急 |
| **Webhook / API** | システム間 | - | 他システム連携 |

「**重要度** × **緊急度** × **アプリ起動中か**」でチャネルを選ぶ。

## 通知設計の 5 つの問い

各通知について:

1. **誰**に送るか (受信者の関心)
2. **何**を伝えるか (1 文で)
3. **なぜ**送るか (受信者の利益、送信者の利益どちらが主?)
4. **いつ**送るか (今 / 後で集約 / 朝一番など)
5. **どうしたら止められる**か

「送れるから送る」は 90% 不要。

## トースト / Snackbar

→ [[Interaction-Patterns]]

操作直後のフィードバック:

```
✓ 保存しました                          [取消]
✗ エラー: ネットワークに接続できません    [再試行]
```

設計指針:
- **4〜6 秒**で自動消滅 (重要なら長く)
- 一度に**最大 3 つ**まで
- アクションは **1 つ**まで
- 重要 (Undo) なら**残留**するエラー型を使う
- 画面隅に表示 (邪魔しない)

トーストは見落とされる前提。**致命的な情報は別チャネル**。

## インアプリ通知センター

ベル型アイコンの定番:

```
🔔 (3)
  ↓
  ──────────────────
  • Alice があなたをメンションしました   [2 分前]
  • 注文が発送されました                [今日]
  • Bob があなたのコメントに返信しました   [昨日]
  ──────────────────
  [ すべて既読 ]  [ 通知設定 ]
```

設計指針:
- **未読/既読**を視覚的に区別
- 個別に既読化 / すべて既読
- 種類別フィルタ (メンション・更新・お知らせ)
- クリックで**該当場所へ移動**
- 履歴は数週間保持

## プッシュ通知

最も強力 = 最も慎重に。

### 許諾の取り方

❌ 起動直後に「通知を許可しますか?」 ─ ほぼ拒否される

✅ 価値が伝わってから:
```
[ 注文しました ]
   ↓
[ 配送状況の更新を通知で受け取れます ]
[ 通知を有効にする ]  [ あとで ]
   ↓ ユーザーが OK
[ OS の許諾ダイアログ ]
```

**プリ許諾 (pre-permission)** で OS ダイアログの前にユーザーの意図を確認。一度拒否されると**再表示が困難**。

### 通知内容

- タイトル: 短く意味あり (「Alice がメッセージを送信」)
- 本文: 文脈を補足
- 画像 / アクション (Reply, Like) を可能なら
- ディープリンク: 開いたら**該当画面**へ直行

### 頻度制御

- 連続通知の**集約**: 「3 件のメッセージ」にまとめる
- **静音時間**: 23時〜7時は送らない (ユーザーのタイムゾーン)
- 種類別 ON/OFF
- フリークエンシーキャップ

## メール通知

### トランザクショナル (操作トリガ)

- 登録確認
- 注文確認
- パスワードリセット
- 重要な変更通知

**信頼性が最重要**: 数分以内に届く、SPF/DKIM/DMARC 設定。

### マーケティング (定期)

- ニュースレター
- プロモーション
- 定期サマリ

**オプトイン必須**、ワンクリック解除。CAN-SPAM 法、GDPR、特定電子メール法を遵守。

### メール設計

- 件名は**40 字以内**(モバイルで切れる)
- プレヘッダー (件名横の補足) を活用
- 主要 CTA は**画面外に出ないように上部**
- Plain text バージョンも提供
- ダークモード対応 (`color-scheme: light dark`)
- 画像は**Alt テキスト**(画像ブロック対策)

## 通知設定 UI

ユーザーが**チャネル × 種類のマトリクス**で制御できるように:

```
                  Push   Email   InApp
新規メッセージ      ☐    ☑      ☑
メンション         ☑    ☐      ☑
週次サマリ          -    ☑      -
プロダクト更新       -    ☐      ☑
```

- デフォルトは**控えめ**に
- グループまとめて ON/OFF
- カテゴリの**重要度説明**
- 1 か所で完結 (各画面に分散させない)

→ [[Settings-Preferences]]

## バナー / アラート

画面上部の常設帯。**継続的な状態**を示す:

```
[ ⚠ メンテナンス: 5/3 02:00〜04:00 ]
[ 📦 接続が切れています。オフラインモードで作業中... ]
[ 🔒 パスワードの有効期限が間近です: 残り 3 日  [変更] ]
```

設計指針:
- **閉じれる**こと (一時的に隠せる)
- 緊急度を**色**で区別 (青情報 / 黄注意 / 赤警告)
- 主要 CTA を併設
- アクセシビリティ: `role="alert"` で SR に伝える

## 集約と頻度

### バッチ送信

5 件のいいねを 5 通でなく:
> 「Alice、Bob、Charlie の 3 人があなたの投稿に反応しました」

### Digest (まとめ)

毎日 / 毎週 1 回のサマリ:
> 「今週のハイライト: 12 件のコメント、3 件のメンション、5 件の更新」

「都度通知」をやめると満足度が**上がる**ことが多い。

### サイレントウィンドウ

ユーザーのタイムゾーン基準で深夜・早朝送信を避ける。

## 失敗パスの設計

- 通知配信失敗時のリトライ (Push, Email)
- 開かれていない通知の**フォロー**(別チャネルで)
- バウンス (届かないメール) のクリーンアップ

## アクセシビリティ

→ [[Accessibility]]

- アラート: `role="alert"` または `aria-live="assertive"`
- 通知トースト: `aria-live="polite"`
- 視覚 + 音/振動を**併用**(色覚 / 音声依存ユーザー)
- 重要通知は**消える前に**ユーザーが認識できる時間を確保

## プライバシー

- ロック画面通知: 内容を出すか / 件数だけか
- メール本文に**機密情報を出さない**(URL から認証経由で見せる)
- プレビュー画像が**意図せず**機密を映していないか

→ [[Security]] / [[../40-Bridge/Ethical-Design]]

## アンチパターン

- 起動直後の**通知 + 位置情報 + カメラ**連発許諾
- マーケティング目的の**プッシュ濫用**
- 「通知を見るには通知 ON」のループ
- 設定 UI が**深くて見つからない**
- 全部既読が**ない**(1 つずつクリック)
- 解除リンクが**1 ヶ所しかない**(送信元アドレス変更で再開)
- メール件名が**200 字**

## チェックリスト

- [ ] 各通知の**目的と頻度**が明確か
- [ ] チャネルが**重要度に合致**しているか
- [ ] 許諾を**価値提示後**に取っているか
- [ ] 集約 / Digest を活用しているか
- [ ] 設定 UI が**1 か所**で完結するか
- [ ] サイレント時間 / タイムゾーンを尊重しているか
- [ ] 解除が**1 クリック**でできるか
- [ ] アクセシビリティ (aria-live, 色 + アイコン) を満たすか
