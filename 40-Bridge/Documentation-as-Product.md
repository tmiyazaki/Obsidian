# プロダクトとしてのドキュメンテーション

## 一行で

> ドキュメントは「**書いたら終わる成果物**」ではなく「**ユーザーがそこで仕事を完了する UI**」。コードと同じく**設計・テスト・改善**の対象。

## なぜ重要か

ドキュメントの質は採用率を決めます。良い API も使い方が分からなければ使われない。良いライブラリも README が古ければ捨てられる。良いプロダクトも社内ドキュメントが無ければ**新人が立ち上がらない**。

ドキュメントは:
- **学習曲線**を平らにする
- **問い合わせを減らす** (Self-Service)
- **属人化を解消**する
- **意思決定の根拠**を残す

それでも軽視されがちなのは「**書く時間が無い**」ではなく、**書く価値が見えていない**から。

## 4 つのドキュメントタイプ (Diátaxis フレームワーク)

```
                  実用 ⇄ 理論
                  ─────────
              │
   学習指向   │  Tutorials (実用) | Explanation (理論)
              │
   作業指向   │  How-to Guides (実用) | Reference (理論)
              │
              ─────────
```

### 1. Tutorials — 学習者を**最初の成功**へ

「**やってみる**」過程。新規ユーザー向け。
- ステップごとに**動く**
- 例外パスは扱わない (本筋に集中)
- 完了感を重視

### 2. How-to Guides — 既知のゴールに**最短で**

「X を達成する方法」。**目的指向**。
- 前提知識を仮定してよい
- ステップ + 注意点
- ゴールが**1 つ**

### 3. Reference — 正確な記述

API、CLI フラグ、設定キー。**完全性**重視。
- アルファベット順 / カテゴリ順
- 引数・戻り値・例
- 自動生成と相性良し (TypeDoc, Sphinx, OpenAPI 等)

### 4. Explanation — 背景・設計判断

「**なぜそうなっているか**」。長期で価値が出る。
- アーキテクチャの決定理由
- トレードオフ
- 歴史的経緯

これら 4 つを**混ぜない**ことが重要。チュートリアルに API 全リファレンスを混ぜると、学習者は迷う。

## ドキュメントの 4 つの観客

1. **新規ユーザー** — Tutorial が刺さる
2. **既存ユーザー** — How-to で素早く解決
3. **デバッガー** — Reference でエラーを調べる
4. **意思決定者** — Explanation で「なぜ?」を理解

各観客の入口を**明示**する。

## 良いドキュメントの性質

### 1. 入口が見える

検索可能、トップから 2 クリック以内、適切な見出し。
README に「次に読むべき場所」を必ず明記。

### 2. 動く例 (Runnable Examples)

コピペで動く例 = 信頼の最大原資。
- そのまま貼って動く (省略しない)
- 出力例も載せる
- バージョンとセット

### 3. 真実 (Up-to-date)

古いドキュメントは**ないより悪い**(嘘を信じさせる)。
- コードと同じリポジトリ
- 自動生成可能なら自動化
- 「最終更新」の表示

### 4. 検索可能

- 用語が一貫
- 同義語の併記 (`/glossary` で検索ヒット率向上)
- 全文検索 (Algolia DocSearch 等)

### 5. 簡潔と網羅のバランス

- 95% のユーザーに必要なものを**前**に
- エッジケースは**後ろ**に
- 「**Quick Start**」を必ず先頭に

## README の標準構成

```
# プロジェクト名

1 文の説明 (これは何か)
バッジ (CI, バージョン, ライセンス)

## なぜ?
解決する問題

## クイックスタート
3〜5 ステップで動く例

## ドキュメント
詳細へのリンク

## サポート対象
バージョン、プラットフォーム

## 貢献
CONTRIBUTING.md へ

## ライセンス
```

冒頭 3 秒で「**自分のプロジェクトに使えるか**」判断できるべき。

## ADR (Architecture Decision Record)

> 「なぜこの設計を選んだか」の記録。

```markdown
# ADR-0042: 認証に JWT ではなく Session Cookie を選んだ

## ステータス
採用 (2026-04-15)

## 文脈
クッキーベース認証と JWT で議論。BFF パターンを採用し、フロント直接ではなく
サーバー経由で API を叩く構造。

## 決定
HttpOnly Session Cookie を採用。

## 結果
- Pros: XSS 経由のトークン漏洩が困難、サーバー側で即時失効可能
- Cons: モバイルアプリ用には別途トークン発行 API が必要

## 代替案
- JWT (Bearer): 拒否 - クライアント保存先 (LS) が XSS で漏れる
- Session + JWT 併用: 複雑度高
```

書いておくと半年後に「**なぜこうした?**」を再議論しなくて済む。

## OpenAPI / GraphQL Schema

API ドキュメントは**スキーマから自動生成**:
- OpenAPI Spec → Swagger UI / Redoc
- GraphQL Schema → GraphiQL / Apollo Studio
- TypeScript types → typedoc

スキーマがあると:
- クライアント SDK 自動生成
- 型安全なフェッチ
- Mock サーバー
- 契約テスト

ドキュメントとコードの**乖離が起きにくい**。

→ [[../10-Coding/API-Design]]

## ドキュメンテーションサイト

選択肢:
- **Docusaurus** (Meta, React)
- **Mintlify** (商用)
- **VitePress / Nextra** (軽量)
- **Sphinx + Read the Docs** (Python 系)
- **MkDocs** (Markdown, 軽量)
- **GitBook**

選ぶ基準:
- バージョニング (旧版を残せる)
- 全文検索
- 多言語対応
- API リファレンス自動生成

## ドキュメントテスト

書いたら終わりではなく、**テスト**する:

### 1. リンクチェック

死リンクを CI で検出 (`linkcheck`, `lychee`)。

### 2. コード例の実行

ドキュメント中のコードブロックを実際に実行 (`doctest`, `mdtest`)。

### 3. ユーザビリティテスト

新人に「これを読んで X してみて」と頼み、詰まる箇所を観察。

→ [[../30-Interface/User-Research]]

### 4. 解析

ページごとの離脱率・検索クエリで「**ユーザーが何を探して見つけられないか**」を発見。

## 内部ドキュメントの戦略

### 「Source of Truth」を 1 つに

- アーキテクチャ → ADR
- API → OpenAPI Schema
- コンポーネント → Storybook
- 業務用語 → Glossary
- 運用手順 → Runbook

複数箇所に同じ内容があると**乖離して全て腐る**。

### Living Documentation

文書を**自動生成 or 自動同期**:
- TypeScript の型 → API ドキュメント
- テスト → 仕様 (BDD)
- DB スキーマ → ER 図
- Storybook → デザインシステムドキュメント

人間が手で更新する量を減らす。

### Onboarding Doc

新人が**初日に動かせる**ガイド:
1. 環境構築
2. テスト実行
3. ローカル起動
4. 初コミット手順

ここで詰まると初週の生産性がゼロになる。

## アンチパターン

- README が**インストール方法だけ**
- API ドキュメントが**型だけ** (例も背景もない)
- "TODO: 後で書く" が放置
- 古いバージョンのドキュメントが**最新**として表示される
- スクリーンショットが**5 年前**の UI
- 過剰な前置き (「このプロジェクトは、現代のソフトウェア開発の現場で…」)
- 検索しても**同義語**で見つからない

## チェックリスト

- [ ] **4 タイプ** (Tutorial/How-to/Reference/Explanation) の役割が分離しているか
- [ ] README が**3 秒**で目的を伝えるか
- [ ] **動くコード例**が含まれているか
- [ ] 重要決定が **ADR** に残っているか
- [ ] 自動生成可能なものは**自動化**されているか
- [ ] リンク・コード例の**自動テスト**があるか
- [ ] 検索クエリ分析で**抜け**を補強しているか
