# ロードマッピングと優先順位付け

## 一行で

> 何を**先に**作るかは何を作るかと同じくらい重要。「機能リスト」ではなく「**学習計画**」としてのロードマップ。

## なぜ重要か

時間と人手は有限です。優先順位付けが甘いと:
- 重要でない機能に**時間が溶ける**
- 主要 KPI が**動かない**
- チームが「何のため」を見失う
- ステークホルダーの**声の大きさ**で動く

良いロードマップは:
- 「**今四半期の主要な仮説**」を共有する
- 機能でなく**成果**を約束する
- 学んだら**変えられる**

## 「**機能ロードマップ**」の罠

```
Q1: 機能 A
Q2: 機能 B
Q3: 機能 C
Q4: 機能 D
```

問題:
- 機能 A が**KPI を動かさなかった**ら? B に進む?
- 6 ヶ月後の市場が変わっていたら?
- ステークホルダーが**約束**として受け取る → 後で変更できない

## アウトカムロードマップ

成果ベースで書く:

```
Q1: 新規ユーザーの**初回タスク完了率**を 30% → 50% に
Q2: **B2B 契約**の月次新規を 5 → 15 件に
Q3: **モバイル離脱率**を 50% → 30% に
Q4: ...
```

「機能 A を作る」ではなく「**この成果を出す**」。手段は柔軟に。

## Now / Next / Later (Janna Bastow)

3 段階の確度を区別:

```
Now (確定)        : 着手中・確定 (詳細あり)
Next (準備中)    : 次の候補 (中程度の詳細)
Later (検討中)   : アイデア (粒度大、変動あり)
```

具体的な**日付**を入れない。確度に応じた**情報粒度**を持たせる。

## OKR (Objectives & Key Results)

Google 由来のフレーム:

```
Objective: ユーザーが製品を**愛する**
  Key Result 1: NPS 30 → 50
  Key Result 2: 月次解約率 5% → 2%
  Key Result 3: 機能リクエストの**「あったらいい」 → 「これが好き」**割合 20% → 50%
```

- Objective: 定性的・感情的
- Key Result: 定量的・測定可能
- 通常 70% 達成が「成功」(100% を狙うと低めに設定する)

## 優先順位付けフレーム

### RICE

→ [[Discovery-and-Validation]]

```
Score = Reach × Impact × Confidence / Effort
```

### MoSCoW

- **Must Have** (必須)
- **Should Have** (重要だが必須でない)
- **Could Have** (あったらいい)
- **Won't Have** (今期は対象外、後で)

「**Won't have**」を明示すると期待管理が楽になる。

### Cost vs Value マトリクス

```
       高 Value
        │
        │ 🟢 Quick Wins   │ 🟡 Big Bets
        │ (即やる)         │ (計画的に)
   低 ──┼──────────────────┼── 高 Cost
        │ 🔴 Avoid         │ 🟠 Time-Sinks
        │ (やらない)        │ (避ける)
        │
       低 Value
```

Quick Wins から着手、Big Bets を計画、他は捨てる。

### Kano モデル

→ [[Discovery-and-Validation]]

Basic / Performance / Excitement で機能の性格を分類。

### Effort vs Confidence

実装コストと**確信度**で:
- 確信高 + Effort 低 = 即着手
- 確信高 + Effort 高 = 計画
- 確信低 + Effort 低 = 実験で検証
- 確信低 + Effort 高 = 着手しない

「確信」を測るには**ディスカバリ**が必要 → [[Discovery-and-Validation]]

## ロードマップに含めるべき要素

```
1. 戦略の文脈
   ├ 会社の北極星指標 (North Star)
   ├ プロダクトミッション
   └ 今四半期の重要 OKR

2. 直近 (Now)
   ├ 着手中のテーマ
   ├ 期待する成果
   └ 検証中の仮説

3. 次の候補 (Next)
   └ 概要と検証段階

4. 検討中 (Later)
   └ アイデア・課題

5. 対象外 (Won't Have)
   └ 期待管理のため

6. 制約・依存
   └ 法規制・大型契約・リソース
```

## ステークホルダー対応

→ [[Critique-Culture]]

### 期待管理

- 確定とアイデアを**明確に分ける**
- 日付ではなく**期間**(Q1, Q2)
- 変更可能性を**前置き**

### 「いつ完成?」への対応

```
"この機能はいつ?"
→ "現在 Next にあります。Q2 の優先度 3 つを終えた後、判断します。"
```

詳細を求められたら**ディスカバリ段階**を共有(検証 → 実装の段階を見せる)。

### 「これを最優先で」

社内で**新機能要望**は絶え間ない。**断る筋立て**を持つ:

- 「現在の Now を終えてから判断します」
- 「他に何を後回しにしますか?」 (ゼロサム)
- 「データで価値を確認しましょう」

## ロードマップの公開度

| 公開先 | 詳細度 |
|---|---|
| 経営層 | 戦略 + 主要 OKR |
| 全社員 | 四半期 OKR + Now / Next |
| 顧客 (公開) | テーマレベル(機能名は控える) |
| 競合・公開 | 抽象的なビジョンのみ |

過度な公開は**期待を膨張**させ、後の変更で**信頼を毀損**する。

## ロードマップのライフサイクル

```
[ 計画 ]    四半期始め、OKR 策定
    ↓
[ 実行 ]    週次レビュー、調整
    ↓
[ 検証 ]    OKR 達成度を測定
    ↓
[ 反省 ]    四半期末、何を学んだか
    ↓
[ 計画 ]
```

「**学んだこと**」が次期の入力。失敗を**ロードマップに反映**する文化が必要。

## チーム構造との関係

### Team Topologies (Skelton & Pais)

- **Stream-aligned**: 顧客フローを担当 (機能チーム)
- **Platform**: 共通基盤を提供
- **Enabling**: 他チームを支援
- **Complicated Subsystem**: 高度技術領域 (ML、暗号)

ロードマップは**チームごと**にある。会社全体は**統合ロードマップ**で重複・依存を可視化。

### コンウェイの法則

「組織構造はソフトウェア構造に映る」。**チーム分割が悪いとアーキテクチャも悪化**する。
ロードマップ立案時に「**このタスクは誰が担う**」「**他チームに依存していないか**」を確認。

## 短期 vs 長期

```
60-70% : Core (主要 OKR、確度高)
20-30% : Adjacent (隣接、新領域)
10%    : Transformational (Big Bets、長期)
```

Google 式の **70:20:10**。すべてを安全策にせず、**長期の賭け**を含める。

## アンチパターン

- 機能リスト型ロードマップ(成果なし)
- 1 年の細部スケジュール(必ず変わる)
- 「**Must**」だらけ (優先度なし)
- ステークホルダーの**最後の一声**で動く
- 振り返りなし(学びが蓄積しない)
- 公開ロードマップで**機能 + 日付**を約束
- OKR が達成可能すぎ or 不可能すぎ

## チェックリスト

- [ ] **成果ベース**(機能でなく)で書かれているか
- [ ] **Now / Next / Later** で確度が分かるか
- [ ] OKR が**測定可能**で**北極星と整合**するか
- [ ] **Won't Have** が明示されているか
- [ ] 公開度合いと粒度が**ステークホルダーに合致**しているか
- [ ] 四半期末の振り返りが**次期に活きる**か
- [ ] 70:20:10 の**バランス**があるか
