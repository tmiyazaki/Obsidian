# 批評文化とフィードバック

## 一行で

> 良いプロダクトは「良い人」ではなく「**良い対話**」が作る。批評は**人格攻撃**でも**沈黙**でもなく、**作品を一緒に育てる協働行為**。

## なぜ重要か

クリエイティブな仕事の質は**フィードバックの質**で決まります。
- 沈黙が支配する → 凡庸な作品が量産される
- 攻撃的批評が横行 → 萎縮、提出回数が減る
- 言葉なきうなずき → 改善の機会を逃す

良い批評文化はチームを育て、プロダクトを進化させ、心理的安全性を支えます。

## 心理的安全性 (Psychological Safety)

> 「**ばかげた質問・反対意見・失敗の告白**を、安心して出せる状態」 — Amy Edmondson

Google の Project Aristotle が「効果的なチームの最大の予測因子」と結論。**スキルではなく対話の質**が決める。

心理的安全性の高いチームは:
- 悪い知らせを早く共有できる
- 多様な視点が出せる
- 学習が速い
- 創造性が高い

## 批評の 3 階層

### 1. リアクション (反応)

「いいね」「すごい」「面白い」 ─ 印象。
価値: 軽いが、**沈黙よりは遥かにマシ**。

### 2. 評価 (判断)

「このボタンは目立ちすぎる」「ここの命名は曖昧」
価値: 改善ポイントの指摘。**主観であることを明示**。

### 3. 批評 (構造的)

「設計目的は X だが、現状は Y を強調している。Z を試すと A の課題は解けるが B のリスクがある」
価値: **目的・現状・代替案・トレードオフ**を語る最高品質。

設計レビュー・コードレビューでは 3 番を狙う。

## 与え方 (フィードバック)

### Yes, And

否定だけでなく**代案を添える**:

```
❌ "これじゃダメだ"
✅ "これだと X が伝わらない気がする。Y にすると Z は強まるが、A のリスクが出る"
```

### "I" メッセージ

主観であることを表す:

```
❌ "これは混乱を呼ぶ"
✅ "私はここで一瞬迷った。なぜなら…"
```

相手の防衛を下げる効果。

### 重要度ラベル

→ [[../10-Coding/Code-Review]]

```
[blocking] 認証バイパスがあります
[suggestion] 命名を userIds にすると単複が明確
[nit] 末尾空白
[question] この設計を選んだ背景を知りたい
```

何が**必須**で何が**気が向いたら**かが伝わる。

### Sandwich は罠

「ほめる → 指摘 → ほめる」は**形式的だと見透かされる**。本物のほめが薄れ、指摘が弱まる。

代替: **ほめは別の場面で十分に**、指摘の場では**指摘に集中する**。

### 場所を選ぶ

- 公開: 全体の学習機会になる質問・議論
- 個別: 個人のパフォーマンス・センシティブな話題

「公開で叱る」は最悪。チーム全体の発言意欲を削ぐ。

## 受け方 (フィードバック受領)

### 反射的に防衛しない

「でも」が出そうになったら 3 秒待つ。指摘の**意図**を聞き返す:

> 「具体的にどこで違和感がありましたか?」

### 受領 ≠ 同意

すべての指摘を受け入れる必要はない。
- 受け入れる
- 議論する
- 却下する (理由を返す)

「**沈黙**」が最悪。指摘者は「無視された」と感じる。

### 感謝する

指摘は**コスト**を払って書かれている。「ありがとう」は文化の潤滑油。

## デザインクリティーク (Design Critique) のフォーマット

### 構造例

```
1. プレゼンタが文脈を共有 (3 分)
   - 何のためのデザインか
   - 制約 (時間・技術・ブランド)
   - 解決したい課題

2. 静かに見る (2 分)
   - 各自が観察し、メモ

3. 質問の時間 (5 分)
   - 評価ではなく**質問だけ**
   - 「この色を選んだ理由は?」

4. フィードバック (15 分)
   - 良かった点 → 改善ポイント → 提案
   - 「I」メッセージで

5. プレゼンタの回答 (5 分)
   - 何を持ち帰るか、何を保留するか
```

時間枠を切ることで議論が**発散しない**。

### "Like / Wish / Wonder" フレーム

```
Like: 「ヘッダの階層がよく機能している」
Wish: 「主要 CTA がもう少し目立つと…」
Wonder: 「モバイルではこの構造はどう変わる?」
```

肯定・改善希望・好奇心を**同じフォーマット**で表現できる。

## コードレビュー文化

→ [[../10-Coding/Code-Review]]

特に重要なポイント:
- **設計レベル**で議論する (フォーマットは自動化)
- **PR を小さく**保つ
- **質問で介入**(断定しない)
- **良い点も**言う
- レビュー時間を**短く**(24 時間以内が目安)

## RFC / Design Doc 文化

大きな決定は文書化して**非同期で**レビュー:

```
タイトル: 認証システムの再構築
著者: Alice
レビュアー: Bob, Carol, David

背景:
- 現状の Session ベースが…

提案:
- JWT に移行する

代替案:
- Session を継続: コスト低、機能制約
- Passkey: 将来性高、移行コスト大

意思決定:
- 今期は JWT、来年 Passkey 検討

タイムライン:
- 設計レビュー: 5/15
- 実装: 6/1〜
```

→ [[Documentation-as-Product]] / [[Tech-Debt]]

会議より**書く**ほうが多くの場合効率的。発言できない人 (時差・性格) も参加できる。

## ブレインストーミングの落とし穴

「ブレストで最高のアイデアが出る」は**実証されていない**:
- 集団思考 (Group Think) で平均化される
- 声の大きい人に引っ張られる
- 並行思考が発散する

代替: **Silent Brainstorming** (個人で書き出して合流)、**Crazy 8s** (8 分で 8 案)、**Reverse Brainstorming** (「失敗させるには」)。

## 反対意見の出し方

- **アイデア vs 人**: アイデアを批判、人格を攻撃しない
- **一人の反対**: 早めに表明 (後出しは信頼を損なう)
- **公開での同調 → 個別での反対**: 危険信号

Amazon の "**Disagree and Commit**" 文化:
> 「反対意見を**最大限**主張する。決まったら**全力で**支援する」

## 多様性とフィードバック

→ [[Inclusive-Design]]

- 文化によって**直接さ**が違う (北欧・米国 vs 日本・東アジア)
- ジュニアが**シニアに**指摘しづらい構造
- マイノリティの**声が拾われる**仕組み

ファシリテータが「**まだ発言していない人**」を意識的に振る、ラウンドロビン形式、匿名フィードバックなど。

## 失敗の文化

### Blameless Postmortem

→ [[../10-Coding/Observability#ポストモーテム]]

事故の原因を**人**ではなく**システム**に求める:

```
❌ "Bob がデプロイミスした"
✅ "確認なしで本番デプロイできる仕組みになっていた → Required Review 追加"
```

「誰が悪い」を問わないことで、**正直な共有**が可能に。

### Pre-Mortem

決定**前**に「この計画は失敗した。なぜ?」を全員で書き出す。失敗パターンが事前に見える。

## ツール

- **Figma** コメント / 反応 (絵文字 + 文)
- **GitHub** PR レビュー / Discussions
- **Notion** / **Confluence** 文書 + コメント
- **Slack** スレッド / 絵文字反応
- **Loom** 非同期動画フィードバック (微妙なニュアンス)

ツールは文化を補助するだけ。**文化が先**。

## アンチパターン

- 公開 Slack で**個人を非難**
- 沈黙のまま PR をマージ ("LGTM" だけ)
- 上司の意見が**自動で勝つ**
- 「**意見を求める**」と言いつつ既に決定済み
- ブレストで**声が大きい人**に支配される
- 形式的な「Sandwich フィードバック」
- 失敗を**個人の責任**にする犯人探し
- "**Sealioning**" (善意を装った執拗な質問攻撃)

## チェックリスト

- [ ] 心理的安全性が**測定**されているか (定期サーベイ等)
- [ ] レビュー時に**重要度ラベル**を使っているか
- [ ] フィードバックに**理由・代案**が含まれているか
- [ ] 大きな決定は**文書化**されているか (RFC/ADR)
- [ ] 多様な声が**拾える**仕組みがあるか
- [ ] ポストモーテムが**Blameless** で運営されているか
- [ ] **発言できない人**にも機会があるか
