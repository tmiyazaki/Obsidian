# プロダクトとしてのマイグレーション

## 一行で

> マイグレーションは「**1 回のイベント**」ではなく「**プロダクトの寿命に何度も発生する継続的な仕事**」。設計・運用・ユーザー体験のすべてが対象。

## なぜ重要か

DB スキーマ、フレームワーク、API バージョン、UI、ユーザー設定 ── マイグレーションはあらゆる層で起きます。雑なマイグレーションは:
- ダウンタイム
- データ消失
- ユーザーの**信頼喪失**
- 他チームの作業ブロック

良いマイグレーション戦略はプロダクトの**進化能力**そのもの。

## マイグレーションの種類

### 1. データベーススキーマ

→ [[../10-Coding/Database-Design]]

列追加、型変更、インデックス、テーブル分割。

### 2. コード / フレームワーク

React 17 → 18、Vue 2 → 3、Rails 6 → 7、内部ライブラリ。

### 3. プラットフォーム / インフラ

AWS → GCP、Heroku → Kubernetes、IDC → Cloud。

### 4. API / 契約

v1 → v2 (REST バージョン)、GraphQL スキーマ変更、メッセージフォーマット。

### 5. UI / UX

リブランド、新ナビ、フローの再設計。

### 6. ユーザー設定 / データ

旧プランから新プラン、無料 → 有料、コミュニティから移籍。

各層に**共通の原則**がある。

## 共通の原則

### 1. Expand → Migrate → Contract

```
1. Expand   : 新旧両方を**追加**(古いものはそのまま)
2. Migrate  : データを徐々に新形式へ移す
3. Contract : 旧を**削除**
```

例: 列名 `email` を `contact_email` に変える場合:

```
ステップ 1: contact_email 列を追加 (NULL 許可)
ステップ 2: アプリが両方読める / 新規書き込みは両方に
ステップ 3: 既存データを backfill
ステップ 4: アプリが contact_email だけ読み書き
ステップ 5: email 列を削除
```

各ステップは**独立にデプロイ可能**。途中で問題があれば**戻れる**。

### 2. ダウンタイムなし

旧バージョンと新バージョンが**並行稼働できる**設計に。
- DB: 列の追加は OK、即座の削除は ✗ (古いアプリインスタンスがまだ動いている)
- API: バージョニング (v1 と v2 を同時提供)
- フロント: 古いタブが開きっぱなしでも動く

### 3. リバーシブル

可能な限り**ロールバック可能**な設計:
- DROP COLUMN ではなく、古い列を**残しつつ無視**
- データの**コピー**をしばらく残す
- フィーチャーフラグで切替

### 4. バックフィル戦略

既存データを**新形式に変換**する処理:

- バッチ (cron / ジョブ): 規模大きい時、夜間
- インクリメンタル (アクセス時に変換): 移行が長期化
- イベント駆動 (変更があったレコードだけ)

```ts
// Lazy migration: アクセス時に変換
async function getUser(id: string) {
  const user = await db.users.find(id);
  if (!user.contact_email && user.email) {
    user.contact_email = user.email;
    await db.users.update(id, { contact_email: user.email });
  }
  return user;
}
```

長所: 大量バッチが要らない / 短所: 完全移行に時間が掛かる、未アクセスデータは残る

### 5. 観測可能性

→ [[../10-Coding/Observability]]

- 移行の**進捗** (% 完了)
- **失敗** (どのレコードが失敗したか)
- **新旧両方の利用率** (旧の利用が 0 になったら Contract 安全)

## DB マイグレーション詳細

### Online Schema Change

大規模テーブルの ALTER は**ロックして停止**することがある。
ツール: `pt-online-schema-change` (Percona), `gh-ost` (GitHub), Vitess。

新しいテーブルにコピー → トリガで同期 → 切替 → 旧削除、の手順を自動化。

### Migration Tool

- **Rails Migration** / **Laravel Migration**
- **Flyway** (SQL ベース、JVM)
- **Liquibase** (XML/YAML/SQL)
- **Prisma Migrate** / **Drizzle Kit**
- **Atlas** (declarative)

すべてのマイグレーションを**Git に**残す。手動 SQL 直叩きは禁止。

### Idempotent Migrations

同じマイグレーションが複数回走っても安全:

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS contact_email text;
CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);
```

CI で同じスクリプトが偶然 2 回走っても破綻しない。

## API バージョニング

→ [[../10-Coding/API-Design]]

```
v1 を Sunset 通知 (6 ヶ月先)
v2 を提供
クライアントが v2 に移行 (期間設定)
v1 を停止
```

クライアント側のフォールバック例:

```ts
// SDK が両方を実装、サーバーバージョンに合わせる
const order = await api.orders.create(payload);
// 内部で v2 を試し、404 なら v1 にフォールバック
```

## フロント / UI マイグレーション

### 段階的ロールアウト

フィーチャーフラグで:
1. 内部メンバーだけ
2. 5% のユーザー
3. 25%
4. 100%

→ [[../10-Coding/CI-CD]]

各段で**メトリクス監視**(エラー率、コンバージョン、CS チケット)。

### A/B テストとマイグレーション

新旧を比較:
- 主要 KPI (滞在時間、コンバージョン)
- セカンダリ (CS 問い合わせ数)
- セグメント別 (新規 vs 既存)

新 UI が**指標悪化**したら一時退却。「**自分たちが好き**」だけで強行しない。

### 移行ガイダンス

ユーザーへの:
- **告知** (ヘルプ、メール、アプリ内通知)
- **新旧切替** (一定期間)
- **チュートリアル** / 動画
- **FAQ** + サポート体制

「気づいたらシステムが変わっていた」は信頼を毀損する。

## データマイグレーション (ユーザー視点)

### 保存形式の変更

例: 旧プランから新プランへ

- 旧プラン契約者は**そのまま**継続できるオプション
- 移行希望者にはガイドとインセンティブ
- 強制移行は**最終手段**(法的・契約的に必要なときのみ)

### マイグレーションヘルパー

ユーザーが**自分でデータを移行**する UI:

```
[ 新しいワークスペースに移行 ]
  ✓ プロジェクト 12 件
  ✓ メンバー 5 名
  ⚠ ファイル 200 件 (新形式に変換)
  [ 開始 ]
```

進捗・成功・失敗を可視化。失敗したら**リトライ可能**。

## 過去データの扱い

### Read Migration

新コードが**両方の形式を読める**ようにする (旧データは変換せず)。

長所: バッチ不要、安全
短所: 永遠に両形式を扱う負債

### Backfill

過去データすべてを新形式に**変換**する。

長所: 完全移行、コードは新形式だけ扱えばよい
短所: 大量データで重い

### Cutoff Date

ある日付以降だけ新形式。古いデータは**そのまま放置 or アーカイブ**。

長所: シンプル
短所: 古いデータと新しいデータで**機能が違う**

## ロールバック計画

「うまくいかなかったら戻す」の**手順を事前に**:

- ロールバック条件 (エラー率 X% 超 → 即時)
- ロールバック方法 (ボタン 1 つ、または手順)
- データの整合性 (新形式で書かれたデータ、旧コードで読めるか)

> ロールバックを**リハーサルしていないなら、ロールバックできない**。

## ステージングと本番

- ステージングで**本番に近いデータ**で試す
- 本番データのコピーで**負荷試験**
- カナリーで**少しずつ**展開

「ローカルで通った」は本番では通らない。

## 過去のレッスン

- **Big Bang Migration** はほぼ失敗 (一晩で全部切替)
- **後方互換性なし変更** はクライアント全停止
- **Backfill 失敗時の再開設計**を忘れる
- **ドキュメント不足** で誰が何をしたか分からなくなる

## アンチパターン

- マイグレーション = `DROP TABLE` で済ませる
- 手動 SQL を本番で直叩き
- ロールバック計画なし
- ステージングなし
- 並行稼働期間が**短すぎる**(古いクライアントが失敗)
- フィーチャーフラグが残り続け**何百個**
- ユーザーへの告知**なし**
- バックフィルが**夜間バッチ 1 回**で失敗したら朝まで気付かない

## チェックリスト

- [ ] **Expand → Migrate → Contract** で段階化されているか
- [ ] **ダウンタイムなし**で実施できるか
- [ ] **ロールバック計画**があり、リハーサル済みか
- [ ] バックフィル進捗が**観測可能**か
- [ ] 旧の利用率が**0** になってから Contract するか
- [ ] フィーチャーフラグに**期限**があるか
- [ ] ユーザーへの**告知**がされているか
- [ ] ドキュメント (ADR) に決定が残っているか
