# パフォーマンスという UX

## 一行で

> 速さは「**機能**」ではなく「**体験そのもの**」。3 秒の遅延は信頼を失わせ、100ms の停滞は操作感を断絶させる。

## なぜ重要か

ユーザーリサーチで「**遅い**」は**最頻出の不満**。にもかかわらず、パフォーマンスは「最後にエンジニアが頑張る」領域として扱われがち。実際には:

- **デザイン段階**で重さが決まる(画像枚数、フォント数、アニメ複雑度)
- **アーキテクチャ段階**でレイテンシが決まる(SSR/CSR, データ層)
- **コード段階**で実体化する(バンドル、N+1、再レンダリング)

3 領域全てに責任があります。

## 体感に影響する閾値

### 待ち時間の心理学(Nielsen)

| 時間 | 体感 |
|---|---|
| 0.1 s | 「即時」と感じる |
| 1 s | 思考が途切れない上限 |
| 10 s | ユーザーの**注意保持の上限** |

### Core Web Vitals(検索ランキングにも影響)

| 指標 | 何 | 良い | 改善が必要 | 不可 |
|---|---|---|---|---|
| **LCP** | 主要要素表示 | < 2.5s | 2.5–4s | > 4s |
| **INP** | 入力 → 反応 | < 200ms | 200–500ms | > 500ms |
| **CLS** | レイアウトシフト | < 0.1 | 0.1–0.25 | > 0.25 |

### 入力レイテンシ

ボタン押下からフィードバックまで **100ms 以内**が「即時」。それ以上だと「動いた?」と疑い始める。

## デザインがパフォーマンスを決める瞬間

### 画像枚数とサイズ

ヒーローに 4MB の画像を置く判断は、エンジニアの最適化では完全には救えない。
- 必要な解像度を**事前に見積もる**
- ロゴは SVG、写真は WebP/AVIF
- ページに**何枚の画像**が乗るかを意識

### フォント

Web フォントは 1 ファイル数百 KB。**3 ウェイト × 2 ファミリー**で MB 単位に。
- ファミリーは 2 種以内
- ウェイトは 2〜3 種に絞る
- サブセット化(日本語は特に重要)

### アニメーション

過剰なモーションは GPU を喰い、低スペック端末で**ガクつく**。
- 同時動作要素を抑える
- transform/opacity に限定
- `prefers-reduced-motion` でオフ可能

### 第三者スクリプト

タグマネージャ、解析、A/B、チャット、広告 …。**累積 1MB 超え**は普通。
- 必要性を継続的に問う
- async/defer
- 重要な計測以外は遅延ロード

## アーキテクチャでの判断

### レンダリング戦略

| 戦略 | 強み | 弱み |
|---|---|---|
| SSR | 初期表示速い、SEO | サーバ負荷、対話性は別途 |
| SSG | 最速、CDN 配信 | 動的データに弱い |
| ISR | SSG + 部分動的 | 一貫性に注意 |
| CSR | 対話性最強 | 初期表示遅い |
| Streaming SSR | 段階表示 | 実装複雑 |

LCP を最優先するなら SSR/SSG、対話性を最優先するなら CSR、両立を求めるなら Streaming SSR + Hydration の最適化。

### データ層

- **N+1 クエリ**は最も普通の悪化原因
- **キャッシュ**(CDN, アプリレベル, ブラウザ)
- **stale-while-revalidate**: 古いデータを即返し、裏で再取得
- **GraphQL/tRPC**: オーバーフェッチを減らす

### バンドル戦略

- **コードスプリッティング**: ルート単位で分割
- **Tree shaking**: 未使用コードの除去
- **動的 import**: 必要時に読む

## コード最適化の原則

→ [[../10-Coding/Performance]]

要旨:
1. **計測**してから最適化
2. **アルゴリズム**改善が最大効果
3. **キャッシュ**は無効化戦略とセットで
4. **並列・遅延・プリロード**を使い分け

## 体感を上げる工夫(知覚最適化)

実際の速度を変えずに**速く感じさせる**:

### 1. スケルトンスクリーン

灰色プレースホルダ + シマー。**コンテンツが「ある」**と認知されるだけで体感速度が上がる。

### 2. Optimistic UI

サーバー応答を待たず先に UI を更新。失敗時にロールバック。

### 3. 段階表示 (Progressive Hydration)

重要な領域から先に対話可能にする。残りは後で hydrate。

### 4. プリフェッチ

ホバーで次のページの HTML を取りに行く、idle 時にナビ先のデータを温める。

```html
<link rel="prefetch" href="/next-page" />
```

### 5. Skeleton/Shimmer の心理

体感的には**100–300ms** で見せ始める。短すぎるとチラつき、長すぎると「フリーズしてる?」。

## 計測と体制

### Real User Monitoring (RUM)

実ユーザーの計測。Lighthouse スコアは合成計測で、実環境とは乖離する。
- web-vitals.js を仕込み LCP/INP/CLS を送信
- セグメント別に分析(端末、回線、地域)

### Synthetic Monitoring

CI で Lighthouse を毎回回し、**回帰**を検出。
- LCP が悪化したら PR をブロック
- バンドルサイズの予算 (size-limit)

### パフォーマンス予算

- **ページサイズ**: 500KB 以内
- **フォント合計**: 200KB 以内
- **JS バンドル**: 200KB 以内 (gzip)
- **画像**: 1 枚 200KB 以内

予算は**チームの合意**として、新機能ごとに守る。

## アンチパターン

- 「リリース前に最適化する」(手遅れ)
- ローカルだけで計測 → 実ユーザー環境と違う
- **平均値**だけ見る → P75/P95 が悪化していることが多い
- 第三者スクリプトの**累積監視なし**
- アクセシビリティと相反する最適化(モーション削減を無視 等)
