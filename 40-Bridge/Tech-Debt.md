# 技術的負債のマネジメント

## 一行で

> 技術的負債は「**汚いコード**」ではなく「**今 ≠ 将来**の意図的または無意識的な乖離」。**借りていることを認識し、利息を測り、戦略的に返す**。

## なぜ重要か

すべての変更は何らかの負債を作ります。「無借金経営」は不可能でも、「**返済計画のない雪だるま**」は破産します。技術的負債を**見える化**し、**意思決定の対象**にすることが、長期的なプロダクト速度を支えます。

## Ward Cunningham の本来の定義

> 「初版は急いだコードでもいい。次の版で**学んだことを反映**しなければ負債が利息を生む。」

つまり「汚さ」ではなく「**学んだことを反映していない状態**」が負債。

## Martin Fowler の象限

```
                 慎重           無謀
              ┌─────────┬─────────┐
              │            │              │
        意図的 │ "出荷を急ぐ" │ "設計など要らん" │
              │            │              │
              ├─────────┼─────────┤
              │            │              │
        無意識的│ "今分かった" │ "レイヤって何"  │
              │            │              │
              └─────────┴─────────┘
```

- **意図的・慎重**: トレードオフを認識して借金 (許容)
- **意図的・無謀**: 知っていて手を抜く (悪)
- **無意識的・慎重**: 学習で気づく (改善機会)
- **無意識的・無謀**: 教育不足 (チームの課題)

## 負債の種類

### 1. コード負債

- 重複、長すぎる関数、命名の劣化
- → [[../10-Coding/Clean-Code]] / [[../10-Coding/Refactoring]]

### 2. 設計・アーキテクチャ負債

- レイヤ違反、循環依存
- マイクロサービス境界の誤り
- → [[../10-Coding/Architecture-Layers]]

### 3. テスト負債

- カバレッジ不足
- 遅い・脆いテスト
- → [[../10-Coding/Testing-Strategy]]

### 4. ドキュメント負債

- ドキュメントが**古い**
- ADR がない
- → [[Documentation-as-Product]]

### 5. 依存・プラットフォーム負債

- 古いライブラリ、サポート切れバージョン
- 廃止予定 API
- 非推奨フレームワーク

### 6. 知識負債

- 1 人しか分からないシステム (Bus Factor)
- 退職とともに消える知識

### 7. UX 負債

- 古い UI、アクセシビリティ未対応
- ダークパターンの放置
- → [[../30-Interface/Accessibility]] / [[Ethical-Design]]

### 8. データ負債

- 矛盾したスキーマ
- 重複データ
- → [[../10-Coding/Database-Design]]

## 利息の計測

「**負債が今、何にコストを掛けているか**」を見える化:

| 兆候 | 利息 |
|---|---|
| 同じ機能の追加に時間が増える | 開発速度低下 |
| バグ修正が別バグを呼ぶ | 信頼性低下 |
| 新人の立ち上げ時間 | オンボーディング遅延 |
| 「あの人しか分からない」 | 属人性 |
| デプロイ怖い | 変更率低下 |

DORA メトリクス (Lead Time, Deploy Frequency, Change Failure Rate, MTTR) は技術的負債の**間接指標**。

## 認識のためのインベントリ

### Tech Debt Register

```
| ID  | 領域      | 説明                                    | 利息 (1-5) | 返済コスト (1-5) | 優先度 |
|-----|----------|----------------------------------------|-----------|----------------|-------|
| TD-1| 認証     | レガシーセッションを JWT に統一          | 4         | 3              | High  |
| TD-2| UI      | 古い Modal コンポーネント (3 種混在)     | 2         | 2              | Mid   |
| TD-3| Test    | E2E が 30 分、誰も待たない                | 5         | 4              | High  |
```

GitHub Issues / Linear / Notion で運用。**見える化されていない負債は管理できない**。

## 返済戦略

### 1. ボーイスカウト・ルール

> 「来たときより少し綺麗にして帰る」

PR で触れた周辺だけ整理。**累積で**改善する。

### 2. 20% タイム

各スプリントの 20% を負債返済に当てる。継続性が鍵。

### 3. 大規模リファクタ (リライト)

最終手段。**部分的に**やるほうが安全 (Strangler Fig パターン)。
**全書き直しはほぼ失敗**する (Joel Spolsky の警告)。

### 4. リアーキテクチャプロジェクト

特定領域 (認証、決済、UI フレームワーク) を**集中**して直す。前後にスナップショット。

### 5. Stop the Line

新機能を**止めて**負債返済に集中する期間。重大化したときの非常手段。

## 返済の意思決定

### 返すとき

- 触る頻度が**高い**領域
- 利息が**事業速度に影響**している
- ロックインで**新機能が作れない**
- セキュリティ脆弱性が含まれる

### 返さないとき

- 二度と触らない領域
- 近々**書き換え予定**(無駄になる)
- ROI が低い (返済に 1 ヶ月、節約は 1 日)

## チームと事業との会話

「**リファクタしたい**」では予算が下りない。事業価値で語る:

```
❌ 「コードが汚いから書き直したい」
✅ 「現在、新機能 1 つに 3 週間かかっている。
   X の整理で 1 週間に短縮可能。3 ヶ月で投資回収」
```

DORA 指標、チケットのリードタイム、バグ率の**データ**を伴うと説得力が増す。

## 防止 (新たな負債を作らない)

### 1. 設計レビュー

実装前にアーキテクチャをレビュー (RFC, ADR)。
→ [[Documentation-as-Product]]

### 2. コードレビュー

→ [[../10-Coding/Code-Review]]

### 3. 自動チェック

- リンタ / フォーマッタ
- 型検査
- 複雑度メトリクス (Cyclomatic Complexity)
- 重複検出 (jscpd, SonarQube)

### 4. テスト

- カバレッジ最低ライン
- 新規コードはカバー必須

### 5. 依存自動更新

- Dependabot, Renovate で**継続的に**最新化
- 大きな更新は**こまめに**(溜めると地獄)

### 6. アーキテクチャテスト

「ドメイン層からインフラ層を import してはならない」をテストで強制 (ArchUnit, dependency-cruiser)。

## 負債とプロダクトフェーズ

| フェーズ | 戦略 |
|---|---|
| MVP / 初期 | 意図的に多めの負債で速く出す |
| PMF 探索 | 実験コードは**捨てる前提**で軽量に |
| 成長 | 負債返済を**継続的に**始める |
| 成熟 | 負債返済の**枠**を確保、新規は厳密に |
| メンテナンス | 主に依存更新と脆弱性対応 |

「**いつ返すか**」はフェーズ依存。早すぎる返済は事業を遅らせる。

## アンチパターン

- 「**技術的負債** = 汚いコード」と狭く理解
- 全部 P1、誰も着手せず
- 全書き直し ("Big Rewrite")
- 個々のエンジニアが**勝手に**直して PR が膨れる
- 事業と技術が**会話しない**
- 「次のスプリントで」が永遠に来ない
- 負債を**測らず**感情で議論

## チェックリスト

- [ ] 主要負債が**インベントリ化**されているか
- [ ] 利息 (影響) が**数値**で語れるか
- [ ] 各スプリント / リリースで**返済枠**を確保しているか

- [ ] 事業側と**会話**できる言葉になっているか
- [ ] 「触らないコード」を区別しているか
