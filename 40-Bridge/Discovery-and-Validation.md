# プロダクトディスカバリと検証

## 一行で

> 「**何を作るか**」を決める仕事は、「**どう作るか**」より大きく結果を左右する。リスクを**早く・安く**つぶす。

## なぜ重要か

機能をリリースしても**70% 以上は KPI を動かさない**(Microsoft 等の社内研究)。「動くプロダクト」が成功を保証しないため、**作る前**に正しい問いを立てる必要があります。

ディスカバリは:
- ユーザーの**本当の課題**を理解
- 解決法の**実現可能性**を確認
- 採算が**取れる**かを検証
- **作るべきでない**ものを見つける

実装より発見のほうが ROI が高いことが多い。

## 4 つのリスク (Marty Cagan)

すべての機能は次のリスクを抱えている:

1. **Value Risk** ─ 顧客は買う/使うか
2. **Usability Risk** ─ 使いこなせるか
3. **Feasibility Risk** ─ 技術的に作れるか
4. **Viability Risk** ─ 事業として成立するか (規制・コスト)

ディスカバリは**実装前にこの 4 つを検証**する。

## ダブルダイヤモンド (再訪)

→ [[../30-Interface/User-Research]]

```
[ Discover ] → [ Define ] → [ Develop ] → [ Deliver ]
   発散         収束          発散          収束
```

ディスカバリは**前半 (Discover + Define)** に集中。「**何が課題か**」を正しく定義することに**最大限**時間を使う。

## ディスカバリの主要技法

### 1. ユーザーインタビュー

→ [[../30-Interface/User-Research]]

過去の行動を聞く。「将来こうしますか?」より「最後に X したのはいつ?」。

### 2. 観察 (Contextual Inquiry)

利用環境で**実作業を観察**。インタビューでは出ない**暗黙の手順**が見える。

### 3. JTBD インタビュー

→ [[../30-Interface/User-Research]]

「**なぜそれを雇った**」状況・動機・期待を解明。

### 4. アンケート

母集団の傾向。質的洞察を**量的に**確認する補助。

### 5. 解析データ

ファネル・ヒートマップ・セッションリプレイで**何が起きているか**。

### 6. 競合分析

市場にある解の評価。**何が満たされず**にユーザーが諦めているか。

### 7. ジョブストーリー

```
When [状況], I want to [動機], so I can [期待される結果].
```

「**ユーザーストーリー**」より状況を強調。例:

```
When I'm rushing to a meeting,
I want to send a quick update without typing,
so I can let my team know I'll be late.
```

「ボイスメッセージ機能」が見える。

## アイデアの段階的検証

```
[ アイデア ]
   ↓ 価値検証
[ ランディングページテスト ]   "Smoke Test"
   ↓ 関心ありそう
[ プロトタイプ + ユーザビリティテスト ]  実装前
   ↓ 使えそう
[ MVP / Wizard of Oz ]    一部手動でも提供
   ↓ 価値検証
[ 本実装 ]
   ↓
[ A/B テスト ]
```

各段階で「**この仮説が間違っていたら次に進まない**」基準を持つ。

## 主要なディスカバリ手法

### 1. Smoke Test (ランディングページテスト)

機能ができていない段階で**LP だけ**作り、サインアップ率を測る:

```
[ AI が議事録を自動作成します ]
[ メールで先行登録 ]
```

「**100 人来て 30 人登録**」なら検証成功。0 人なら作るな。

### 2. Wizard of Oz

機能を**裏で人間が**やる:
- ユーザーには「AI が回答」と見せ、実は人間が答える
- ユーザーの**反応・要求**を観察
- 完成した実装を作る前に**価値**を確認

### 3. Concierge MVP

最初の数人に**手作業で**サービス提供。
- スケールしないが**学習が速い**
- 何を自動化すべきか見える

### 4. プロトタイプテスト

→ [[../30-Interface/User-Research]]

Figma プロトタイプで**主要フロー**を検証。タスク完了率・離脱箇所を観察。

### 5. RICE スコアリング

機能を比較:

```
Score = Reach × Impact × Confidence / Effort
```

- Reach: 影響を受けるユーザー数
- Impact: 1 人あたりの影響度 (3=大, 2=中, 1=小, 0.5=最小)
- Confidence: 確信度 (100% / 80% / 50%)
- Effort: 工数 (人月)

絶対値より**相対比較**に使う。

### 6. Kano モデル

機能を 3 種に分類:
- **Basic (当たり前)**: ないと不満、あっても満足度上がらない (ログイン)
- **Performance (一元的)**: あるほど満足 (速度)
- **Excitement (魅力的)**: 期待外 = 感動 (新機能)

すべてを基本品質で揃えてから、興奮を加える。

### 7. Opportunity Solution Tree (Teresa Torres)

```
[ 望ましいビジネス成果 ]
        ↓
[ 機会 (ユーザーニーズ) ]   ← 複数並列
        ↓
[ 解決策候補 ]              ← 複数並列
        ↓
[ 実験・検証 ]
```

「**機会と解決策を分ける**」。 「機能ありき」になる罠を防ぐ。

### 8. 5 Whys

症状から**根本原因**へ:

```
Q: ユーザーが離脱する
A: 登録フォームが長いから
Q: なぜ長い?
A: 全情報を初回に集めたいから
Q: なぜ全情報必要?
A: マーケが欲しがる
Q: なぜマーケが欲しがる?
A: セグメント分析のため
Q: なぜ初回に集める必要?
A: ...本当は後で取れる
```

実装前に「**そもそも必要?**」を問う。

## 検証なしで進む判断

すべてに検証は不要。ディスカバリ vs 直接実装の判断:

### 検証する

- 大きな投資 (機能規模・期間)
- ユーザーが**慣れていない領域**
- データに頼れない判断 (新規市場)
- 失敗の代償が大きい(信頼・契約)

### 直接実装する

- 小さな改善 (バグ修正、コピー変更)
- 慣習・ベストプラクティスに従う
- 競合がやっていて**当たり前**
- 検証コスト > 実装コスト

## North Star Metric

プロダクト全体が**追う北極星指標**。「成長」は曖昧。具体的に:

- Spotify: 再生時間
- Airbnb: 予約泊数
- Slack: チームの送信メッセージ数
- Calendly: 予約成立数

下位指標 (登録・PV・MAU) は**北極星に至る経路**として位置付ける。

特性:
- ユーザー価値と**整合**(虚栄指標でない)
- ビジネスと**整合**(売上に繋がる)
- 動かすことが**現実的**

## 意思決定の透明化

ディスカバリの結果を**チームで共有**:
- 動画クリップ(痛い瞬間 30 秒)
- 上位 3 発見 + 推奨アクション
- 代替案・リスク

→ [[Critique-Culture]] / [[Documentation-as-Product]]

## Fake Door / Painted Door

未実装機能のボタンを置く:

```
[ 高度なフィルタ ]
   ↓ クリック
[ "もうすぐ提供します。先行通知をご希望ですか?" ]
```

ユーザー数 / クリック率で**需要を測る**。倫理的には**告知必須**(クリックして「実装中」と分かる前に欺いた感を持たせない)。

## アンチパターン

- 「**ユーザーが言ったから**」直接実装(言うこと ≠ 使うこと)
- 検証なしで**6 ヶ月の機能**着手
- A/B テストの**ベース指標**を決めず後解釈
- 「**既に決まっている**」のにディスカバリの形式
- 競合の機能を**理由なく**コピー
- ステークホルダーの**声の大きさ**で優先度
- 仮説に**反証可能な基準**がない

## チェックリスト

- [ ] **4 つのリスク**(Value/Usability/Feasibility/Viability) を意識したか
- [ ] 仮説に**反証可能な基準**があるか
- [ ] 検証コスト < 失敗コストか
- [ ] **ユーザーの過去の行動**を見たか
- [ ] North Star Metric と**整合**しているか
- [ ] 代替案を**少なくとも 2 つ**比較したか
- [ ] 結果が**意思決定に繋がる**か
