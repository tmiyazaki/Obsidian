# デザインとコードの受け渡し (Handoff)

## 一行で

> Handoff は「**仕様書の引き継ぎ**」ではなく「**両者が同じ語彙で会話し続けるプロセス**」。

## なぜ重要か

Handoff の伝統的な悪い形:

```
デザイナー: 完成した PSD を「投げる」
   ↓
エンジニア: 自分の解釈で実装
   ↓
QA: 「ここピクセル違う」「色が違う」「アニメ無い」
   ↓
往復 → 摩擦 → リリース遅延 → 信頼低下
```

これは**プロセスの問題**であって、ツールでは根本解決しません。

## 良い Handoff の 5 原則

### 1. 同じ語彙で話す

デザインのトークンとコードのトークンが**同じ名前**:
- `color.action.primary` (Figma) ⇔ `--color-action-primary` (CSS)
- `space.4` (Figma) ⇔ `var(--space-4)`

→ [[../20-Design/Design-Tokens]]

### 2. 部品で考える

ページ単位ではなく**コンポーネント単位**で受け渡す。Figma の Component と、コードの Component が**1:1**:

```
Figma:    Button / Primary / Large
Code:     <Button variant="primary" size="large">
Storybook: /docs/Button (両者の状態を網羅)
```

→ [[Component-Driven-Development]]

### 3. 早く何度も

「完成してから渡す」ではなく、**ラフ段階から並走**する:

```
ワイヤー → エンジニア確認(技術的制約)
モック → エンジニア相談(エッジケース・状態)
ハイファイ → 実装と並走
```

エンジニアが終盤に発見する問題(モバイルで破綻、A/B 状態が定義無し、空状態が無い)は**前倒しで潰せる**。

### 4. 静止画で表現できないものを足す

仕様書が静止画だと欠落するもの:
- 状態(loading/error/empty/success)
- マイクロインタラクション(イージング、時間)
- レスポンシブ(ブレークポイントごとの挙動)
- アクセシビリティ(キーボード・SR の振る舞い)

これらは**Figma のプロトタイプ + 添付ノート**で記述、または Storybook で実装後の正本にする。

### 5. 正本を一つに決める

| 何 | 正本 |
|---|---|
| デザイントークン | Figma Variables → トークン JSON(自動同期) |
| コンポーネントの形状 | Figma |
| コンポーネントの実装挙動 | Storybook(コード) |
| アクセシビリティ要件 | コードのテスト |
| 状態の網羅 | Storybook |

「**正本が分散**」が破綻の主因。**役割を決め**、書き換える場所を 1 箇所に。

## 受け渡し時の最低限の確認事項

### コンポーネント単位で

- [ ] 全ての Variant・State がデザインに存在するか
  - default, hover, focus, active, disabled, loading, error
- [ ] レスポンシブ挙動(min-width X 未満で何が起きるか)
- [ ] アクセシビリティ要件(focus order, ARIA, キーボード操作)
- [ ] エッジケース(長文・空・大量データ・画像なし・名前 0 文字)

### 画面単位で

- [ ] 5 状態(空・読込・部分・エラー・理想)
- [ ] 主要 CTA とフォーカス順
- [ ] 文言は実データかプレースホルダか明示
- [ ] 国際化(英語・日本語両方で破綻しない)
- [ ] ダーク/ライトモード

## ツール

### デザイン → 開発

- **Figma Dev Mode**: 値・トークン・コードスニペットの抽出
- **Tokens Studio**: トークン管理 + 各形式へエクスポート
- **Style Dictionary**: トークンを CSS/iOS/Android の形に変換

### 双方向同期

- Figma Variables ⇔ JSON トークン ⇔ コード の自動パイプライン
- GitHub への PR 自動化

### コード → デザイン

- **Storybook MDX**: 実装をドキュメント化
- **Chromatic**: 実装の見た目を Figma にフィードバック

## レビューの相互参加

デザインレビューにエンジニア、コードレビューにデザイナーが**居る**だけで、後段の手戻りが激減する。**最後に一度確認**ではなく、**プロセス全体に共在**する。

## QA フェーズの省力化

最終調整(ピクセル合わせ、フォントウェイト確認、アニメタイミング微調)はデザイナーが**直接コードを修正**できると最速。CSS の小修正くらいはデザイナーも触れる文化が、プロダクトの仕上がりを底上げする。

## アンチパターン

- Figma を「画像のキャンバス」として使う(Variant・Auto-Layout 未活用)
- ハイファイデザイン**直前**にエンジニアと初対話
- トークンを**色名**で命名(`--blue-500` を UI で直使用)
- アニメ・状態・レスポンシブを**口頭**で伝える
- 仕様変更が**Figma だけ**で起き、Storybook が腐る

## チェックリスト

- [ ] デザイントークンが**コードと同じ名前**で揃っているか
- [ ] コンポーネントが**1:1 対応**しているか
- [ ] 全 Variant/State が**両方**に存在するか
- [ ] レスポンシブ・アクセシビリティ・モーションが文書化されているか
- [ ] 正本がそれぞれ**1 箇所**に決まっているか
- [ ] エンジニアが**早期から**関与しているか
