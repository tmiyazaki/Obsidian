# プライバシー・バイ・デザイン

## 一行で

> プライバシーは「**機能の付け足し**」でなく「**設計の前提**」。データを**最小限**取得し、**透明**に扱い、**ユーザー主権**を守る。

## なぜ重要か

データは**負債**でもあります:
- 漏洩リスク = 賠償 + 信頼喪失
- 保存・処理コスト
- 規制違反による課徴金 (GDPR は最大年商 4%)
- ユーザー離脱

「**データは多く集めた方が良い**」は古い思考。**必要十分**に絞ったほうが安全・低コスト・倫理的です。

## Privacy by Design — 7 原則 (Ann Cavoukian)

### 1. Proactive (事後でなく事前)

問題が起きてから対応するのでなく、**設計時に**予防。

### 2. Default 設定で保護

ユーザーが何もしなくても**最も保護的**な設定。
- デフォルトで非公開
- デフォルトで通知 OFF
- デフォルトで分析データ送信なし

### 3. 設計に組み込む

「セキュリティ機能」ではなく「**機能の一部**」として。

### 4. Full Functionality (機能性と両立)

「プライバシー or 機能」ではなく**両立**を目指す。

### 5. End-to-End Security

ライフサイクル全体で保護:
- 収集
- 保管
- 利用
- 共有
- 削除

### 6. Visibility & Transparency

何が起きているか**ユーザーに見える**。

### 7. Respect for User Privacy

ユーザー中心 ─ 利便性ではなく**ユーザーの権利**を最優先。

## データ最小化

「**取得する → 何に使うか証明**」のフローで:

### 必要最小限のフィールド

```
登録: メール + パスワード ✓
登録: メール + パスワード + 名前 + 会社 + 役職 + 業種 + ... ✗
```

後で取れる情報は後で。**初回フォームを最小**に。

→ [[../30-Interface/Forms-and-Input]] / [[../30-Interface/Onboarding-Empty-States]]

### 必要最小限の精度

- 位置情報: 国 / 都市レベルで十分なら、緯度経度を取らない
- 年齢: 「**18 歳以上か**」で十分なら、生年月日を取らない
- メール: ハッシュで十分なら、平文を保存しない

### 必要最小限の保管期間

- セッショントークン: 短命
- ログ: 30 / 90 日
- 取引履歴: 法定保管期間後に削除
- 退会者データ: 即削除 or 一定期間で完全消去

GDPR の「**Storage Limitation**」原則。

## 同意 (Consent) の設計

### 真の同意

```
✓ 自由 (拒否しても主要機能は使える)
✓ 具体 (何の目的か明示)
✓ 情報がある (理解できる説明)
✓ 撤回可能 (いつでも、簡単に)
✗ デフォルトで全部チェック済み
✗ 「同意しないと使えません」と一律
```

### 階層的同意

```
[ 必須 ] サービス提供のため (拒否不可、機能制限)
[ 任意 ] 改善のための解析    (拒否しても OK)
[ 任意 ] マーケティング配信  (拒否しても OK)
```

各カテゴリで個別 ON/OFF。「**全部 ON**」「**全部 OFF**」も**同等の手数**で。

→ [[Ethical-Design]]

## 透明性

### Privacy Policy

法律文書として 30 ページではなく、**人が読める形**で:
- 何を集めるか
- なぜ集めるか
- どこに送るか
- 誰と共有するか
- いつまで保管するか

「**TLDR バージョン**」を冒頭に。長文は補完。

### データダッシュボード

ユーザーが**自分のデータ**を見られる UI:
- アカウント情報
- アクティビティログ
- 共有設定
- 接続したアプリ
- 同意履歴

Google の「**Google アカウント** > **データとプライバシー**」が好例。

### 何が起きているかの即時表示

- 通話中のマイクインジケータ (iOS)
- 位置使用中の表示
- カメラ使用中
- 「Track ID」(クッキー識別子) を可視化するブラウザ拡張

## ユーザー権利の実装

### GDPR / CCPA / 個人情報保護法

すべての主要法は**類似の権利**を保証:

| 権利 | 内容 |
|---|---|
| **アクセス権** | 自分のデータを取得できる |
| **訂正権** | 誤りを訂正させる |
| **削除権** (Right to be Forgotten) | データの削除を要求 |
| **ポータビリティ権** | 構造化形式で取り出し別サービスへ |
| **処理停止権** | マーケ送信などを止める |
| **同意撤回権** | いつでも |

UI で:
- 「**データをダウンロード**」(JSON / CSV)
- 「**アカウントを削除**」(全データ消去)
- 「**マーケ受信を停止**」(1 クリック)

「**問い合わせフォームでお願いします**」は不適切 → 自動化必要。

## データの分類

```
公開           : 誰でも見れる (LP コンテンツ)
内部           : 社員のみ
機密           : 経営情報、契約
極秘           : 個人特定情報、決済、認証
```

各レベルで:
- 暗号化要件 (転送時 / 保管時)
- アクセス制限
- 監査ログ
- バックアップ方針

→ [[../10-Coding/Security]] / [[../10-Coding/Database-Design]]

## Pseudonymization (仮名化) と Anonymization (匿名化)

### Pseudonymization

識別子を**置換**(ID にハッシュなど):
- データは個人特定可能だが、**鍵がないと**特定されない
- 開発・分析用には十分
- 法的には**まだ個人情報**(GDPR では仮名化データも保護対象)

### Anonymization

完全に**戻せない**ように加工:
- k-匿名性 (k-anonymity)
- 差分プライバシー (Differential Privacy)
- 集計のみ提供

「**匿名化されているから安心**」は誤解 ─ Netflix の事例 (匿名データから個人特定された) を参照。

## 暗号化

→ [[../10-Coding/Security]]

### Transit (通信時)

すべて **HTTPS** (TLS 1.3 推奨)。HTTP は禁止。

### At Rest (保管時)

DB の暗号化、ディスク暗号化、バックアップ暗号化。

### End-to-End

サーバ側でも復号できない:
- WhatsApp / Signal のメッセージ
- iCloud Advanced Data Protection

実装複雑だが、**プライバシー最強**。鍵管理が課題。

## 第三者との共有

ベンダー・パートナーへのデータ提供は**契約で縛る** (DPA, Data Processing Agreement)。

- 何を共有するか
- どう使うか
- 漏洩時の責任
- 削除義務

```
Google Analytics, Meta Pixel, etc. を入れる前に
「これは何のデータを送り、第三者で何が起きるか」を明確化。
```

## ロケーション固有 (Data Residency)

地域ごとの法律で**データ保管場所**が制限される:
- EU データは EU 内
- 中国データは中国内
- 日本の個人情報は越境移転の同意

クラウドリージョン選択が**法的義務**になる。

→ [[../10-Coding/Edge-and-Distributed]]

## 子どもとプライバシー

- COPPA (米): 13 歳未満
- GDPR-K (EU): 16 歳未満 (国により異なる)
- 児童ポルノ・グルーミング・搾取の防止

子ども向け / 子どもが触れうるサービスは**追加保護**:
- 親の同意
- 広告ターゲティング禁止
- データ収集最小化

## クッキー・トラッキング

→ [[Ethical-Design]]

- 必須クッキー (セッション・カート) → 同意不要
- 機能クッキー (言語設定) → 軽い情報提供
- 解析・広告クッキー → **明示的同意必須**

「**クッキー同意バナー**」のダークパターン化が問題。EU では 2024 年以降、規制強化。

## ログとデバッグ

→ [[../10-Coding/Observability]]

ログに**個人情報を出さない**:

```
❌ logger.info("User logged in", { email, password, address })
✅ logger.info("User logged in", { user_id_hash })
```

エラーメッセージにメールアドレス・トークンが**漏れがち**。マスク処理を**ライブラリレベル**で。

## アクセス制御

→ [[../10-Coding/Security]] / [[../30-Interface/Permissions-UX]]

社内アクセスも厳格に:
- 最小権限の原則 (PoLP)
- 個人情報を**全社員が**見れる状況を避ける
- アクセスログ・監査
- 退職時の即時アクセス剥奪

## ローカルファースト

→ [[../30-Interface/Real-time-Collaboration]]

可能な処理は**サーバに送らない**:
- 暗号化はクライアント側
- 検索はローカルインデックス
- ML 推論は**端末で**(Apple Intelligence の方向)

サーバに送らないデータは**漏れない**。最強のプライバシー対策。

## 設計レビューでのチェック

機能設計時に必ず問う:

- [ ] このデータは**本当に必要**か
- [ ] **どれくらいの精度**で十分か
- [ ] **何日**保管するか
- [ ] **誰が**アクセスするか
- [ ] **どこに**保管するか (リージョン)
- [ ] 漏洩時に**どう影響**するか
- [ ] ユーザーが**確認・削除**できるか

## アンチパターン

- 「**いつか使うかも**」でデータを集める
- 削除リクエストを**手作業で**処理(自動化なし)
- ログに個人情報を**そのまま**出力
- 「同意」を**ダークパターン**で取得
- 第三者データ共有を**ユーザーに告げない**
- データ保管期間が**永久**
- ベンダーの DPA を**確認しない**
- 子ども保護なし
- 漏洩告知を**遅延**(日本は 3-5 日、EU は 72h 以内)

## チェックリスト

- [ ] データ収集が**最小限**か
- [ ] 保管期間が**明示**されているか
- [ ] **アクセス・削除**が UI から可能か
- [ ] 暗号化 (転送・保管) されているか
- [ ] 第三者との共有が**明示・契約化**されているか
- [ ] ログ・エラーに**個人情報が漏れない**か
- [ ] 同意 UI が**真の同意**を取れているか
- [ ] 子ども保護 (年齢確認等) が必要なら実装されているか
